\section{Data Structures for Pastèque}\label{sec:low-level-datatypes-in-isabelle-llvm}

Pastèque uses nested lists $\iexp{llist\_polynomial}$ and $\iexp{sllist\_polynomial}$ for storing polynomials, a hashset of strings to keep track of used variables $\mathscr{V}$, a partial map of polynomials $\iexp{A}$ and a hashmap for the mapping $\iexp{VN}$.
I could not find fitting data structures in Isabelle-LLVM to refine these high-level types.
I therefore implement custom refinement targets, extending and combining existing refinement assertions from Isabelle-LLVM.

In this section, I make some simplifications to the presented definitions, omitting minor technicalities to present the fundamental concepts in a more concise manner and also to obtain more consistent naming of definitions, compared to the actual source code.
I add footnotes to highlight differences of the presented definitions, compared to the actual implementation, but I do not explicitly annotate simplification where the presented lemma is an equivalent reformulation (in particular renaming).
In addition, most lemmas are formulated using "hfref" (heap-function refinement) notation\footnote{cf. theory \isaname{Isabelle_LLVM.Sepref_Rules}.} in the actual theories.
As I do not introduce hfref notation in the thesis, I instead present Hoare-triples which are directly implied by the respective hfref lemmas.

\subsection{Interface Hierarchy for Refinement Assertions}\label{sec:interface-hierarchy-for-refinement-assertions}

For the implemented data structures to be useful in practice, the data structure might require certain functionality from the contained elements.
For example, the list implementation supports a deep copy operation, for which an existing copy function on the inner elements is required.
Similarly, a hashmap requires the contained elements to support a hash operation.

I use Isabelle's \inlinecode{locale} feature to require specific functionality from refinement assertions of contained elements, so that the implementation of a container data structure can be implemented in a generic way.
This idea is somewhat similar to the concept of typeclasses in, e.g., Haskell but in addition to requiring functionality from a refinement assertion also allows for expressing formal specifications of the required functions.
\begin{itemize}
	\item A refinement assertion $A \dbcolon \tv{a} \rightarrow \tv{b} \rightarrow \iexp{assn}$ can instantiate $\iexp{freeable\_assn}$ if there exists a function $\iexp{afree} \dbcolon \tv{b} \rightarrow \iexp{unit} \app \iexp{llM}$ that frees the elements from memory. The Hoare-triple $\{A \app a \app ai\}(\iexp{afree} \app ai)\{\iexp{emp}\}$ must hold\footnote{The actual definition in theory \isaname{LLVM_Assn_Env} uses $\iexp{MK\_FREE}$ from Isabelle-LLVM which directly implies the presented Hoare-triple.}. Note that pure elements are trivially freeable.
	\item A refinement assertion $A \dbcolon \tv{a} \rightarrow \tv{b} \rightarrow \iexp{assn}$ can instantiate $\iexp{copyable\_assn}$ if there exists a function $\iexp{acopy} \dbcolon \tv{b} \rightarrow \tv{b} \app \iexp{llM}$ that copies an element of type $\tv{b}$.
	      The Hoare-triple $\{A \app a \app ai\}(\iexp{acopy} \app ai)\{\lambda r. A \app a \app ai \ast A \app a \app r\}$ must hold\footnote{The actual definition in theory \isaname{LLVM_Assn_Env} uses $\iexp{COPY}$ from Isabelle-LLVM which implies the presented Hoare-triple.}.
	      All copyable refinement assertions must also be freeable.
	      Pure elements are trivially copyable.
	\item A refinement assertion $A \dbcolon \tv{a} \rightarrow \tv{b} \rightarrow \iexp{assn}$ can instantiate $\iexp{eq\_assn}$ if there exists a function $\iexp{aeq} \dbcolon \tv{b} \rightarrow \tv{b} \rightarrow \iexp{bool} \app \iexp{llM}$\footnote{Booleans are actually refined by 1-bit machine words, but for the thesis I assume a return type $\iexp{bool} \app \iexp{llM}$, instead of $1 \app \iexp{word} \app \iexp{llM}$ for simplicity.} that evaluates to true if both given elements are equal.
	      The Hoare-triple $\{A \app a \app ai \ast A \app b \app bi\}(\iexp{aeq} \app ai \app bi)\{\lambda r. \uparrow(r = (a=b))\}$ must hold.
	\item A refinement assertion $A \dbcolon \tv{a} \rightarrow \tv{b} \rightarrow \iexp{assn}$ can instantiate $\iexp{linorder\_assn}$ if it instantiates $\iexp{eq\_assn}$ and there exists a function $\iexp{alt} \dbcolon \tv{b} \rightarrow \tv{b} \rightarrow \iexp{bool} \app \iexp{llM}$ that evaluates to true if the first element is less than the second element.
	      The Hoare-triple $\{A \app a \app ai \ast A \app b \app bi\}(\iexp{alt} \app ai \app bi)\{\lambda r. \uparrow(r = (a<b))\}$ must hold.
	\item A refinement assertion $A \dbcolon \tv{a} \rightarrow \tv{b} \rightarrow \iexp{assn}$ can instantiate $\iexp{hashable\_assn}$ if there exists a function $\iexp{ahash} \dbcolon \tv{a} \rightarrow 64 \app \iexp{word}$ with a refinement target $\iexp{ahash\_impl} \dbcolon \tv{b} \rightarrow 64 \app \iexp{word} \app \iexp{llM}$.
	      There are no requirements for the given hash function.
\end{itemize}

With these definitions, deep free, deep copy or a lexicographic order on lists can be implemented generically, using $\iexp{afree}$, $\iexp{acopy}$, $\iexp{aeq}$ and $\iexp{alt}$ for element-wise freeing, copying or comparisons.
In particular, if some datatype $\tv{a}$ supports freeing and copying (i.e. it instantiates $\iexp{freeable\_assn}$ and $\iexp{copyable\_assn}$), then a list of elements of type $\tv{a}$ can itself also instantiate $\iexp{freeable\_assn}$ and $\iexp{copyable\_assn}$.
This allows for convenient nesting of data structures without having to reimplement functions at each level of nesting.

\subsection{Linked Lists with Tail Pointers}\label{sec:lists-with-tail-pointers}

This section introduces extensions to Isabelle-LLVMs open list implementation\footnote{cf. theory \isaname{Isabelle_LLVM.LLVM_DS_Open_List}} I have made to obtain a nestable linked list implementation for use in the Pastèque migration to Isabelle-LLVM.
I also discuss some optimizations I have made to avoid having to deep copy lists when using them as arguments of functions that only read from, but do not modify the given lists.

\subsubsection{A Refinement Assertion for Lists}\label{sec:refinement-assertion-for-lists}

To represent lists in LLVM, I reuse existing definitions from Isabelle-LLVM with some modifications.
In the following, assume that $A \dbcolon \tv{a} \rightarrow \tv{b} \rightarrow \iexp{assn}$ is a refinement assertion, implying that $\tv{b}$ is representable in LLVM.

Lists are implemented on $\iexp{llM}$-level as a chain of nodes, where a node carries a value and a pointer to the next node:
$$
	\tv{b} \app \iexp{node} = \iexp{Node} \app (\iexp{val} \dbcolon \tv{b}) \app (\iexp{next} \dbcolon \tv{b} \app \iexp{node} \app \iexp{ptr})
$$
A list in LLVM is a pointer to a node, i.e., a value of type $\tv{b} \app \iexp{node} \app \iexp{ptr}$.
The empty list is represented by a null pointer.
A node with $\iexp{node}.\iexp{next} = \iexp{null}$ denotes the end of a list.

To refine lists of type $\tv{a} \app \iexp{list}$, a refinement assertion of type $\tv{a} \app \iexp{list} \rightarrow \tv{b} \app \iexp{node} \app \iexp{ptr} \rightarrow \iexp{assn}$ is required.
Implementing such a refinement assertion requires some preliminary definitions.

First, a notion of element-wise refinement is given by an assertion $\iexp{list\_aux} \dbcolon (\tv{a} \rightarrow \tv{b} \rightarrow \iexp{assn}) \rightarrow \tv{a} \app \iexp{list} \rightarrow \tv{b} \app \iexp{list} \rightarrow \iexp{assn}$
\footnote{$\iexp{list\_aux}$ mirrors $\iexp{list\_assn}$ as defined in \isaname{Isabelle_LLVM.Proto_EOArray}.}:
\begin{align*}
	\iexp{list\_aux} \app A \app xs \app xsi = & (\iexp{length} \app xs = \iexp{length} \app xsi)                                                                                 \\
	                                           & \ast (\forall i.\ 0 \le i < \iexp{length} \app xs \Rightarrow A \app (xs \app \iexp{!} \app i) \app (xsi \app \iexp{!} \app i)),
\end{align*}
where $xs \app \iexp{!} \app i$ denotes the $i$-th element of list $xs$.
$\iexp{list\_aux}$ can be seen as the characteristic function of a refinement relation between lists $xs \dbcolon \tv{a} \app \iexp{list}$ of abstract elements and lists $xsi \dbcolon \tv{b} \app \iexp{list}$ of concrete elements where for each position, the refinement assertion $A$ holds for the respective abstract and concrete element.
Note that $\tv{b} \app \iexp{list}$ is not representable in LLVM and will not be recognized by the code generator.

Second, a function $\iexp{lseg} \dbcolon \tv{b} \app \iexp{list} \rightarrow \tv{b} \app \iexp{node} \app \iexp{ptr} \rightarrow \tv{b} \app \iexp{node} \app \iexp{ptr} \rightarrow \iexp{bool}$ relates lists of type $\tv{b}$ to segments of lists in LLVM, where the first $\tv{b} \app \iexp{node} \app \iexp{ptr}$ is a pointer to the start of the segment and the second $\tv{b} \app \iexp{node} \app \iexp{ptr}$ is a pointer to the end of the segment.
$\iexp{lseg}$ is recursively defined as
\footnote{$\iexp{lseg}$ is defined in \isaname{Isabelle_LLVM.LLVM_DS_List_Seg}.}
\begin{align*}
	\iexp{lseg} \app xs \app p \app s =
	\begin{cases}
		\uparrow(p = s)                                                                                & \text{, if $xs = [ \app ]$}                        \\
		\uparrow \app \iexp{False}                                                                     & \text{, if $xs \neq [ \app ]$ and $p=\iexp{null}$} \\
		\exists q. p \mapsto (\iexp{Node} \app x \app q) \ast \iexp{lseg} \app \iexp{xs} \app q \app s & \text{, otherwise}
	\end{cases}
\end{align*}
\begin{itemize}
	\item If the given list is empty then both pointers are equal.
	\item If the given list is not empty then $p$ must not be $\iexp{null}$.
	\item If the list is not empty, then $p$ is a pointer to $\iexp{Node} \app x \app q$, where $x$ is the value held by the node and $q$ is the pointer to the next node.
	      Also, for the tail of the list it must hold that $\iexp{lseg} \app \iexp{xs} \app q \app s$.
\end{itemize}

Using $\iexp{list\_aux}$ and $\iexp{lseg}$, a refinement assertion for lists, parameterized by $A$, can be defined by
\footnote{In the actual list assertion $\iexp{cl\_assn}$, defined in theory \isaname{LLVM_DS_Copying_List}, the auxiliary list assertion $\iexp{list\_aux}$ ($\iexp{list\_assn}$ in the theories) is included in a custom $\iexp{olseg}$ definition.}
\begin{align*}
	\iexp{ls\_assn} \app A \app xs \app p = \exists xsi.\ \iexp{lseg} \app xsi \app p \app \iexp{null} \ast \iexp{list\_aux} \app A \app xs \app xsi
\end{align*}
which means that $p \dbcolon \tv{b} \app \iexp{node} \app \iexp{ptr}$ refines $xs \dbcolon \tv{a} \app \iexp{list}$ if there exists a list $xsi \dbcolon \tv{b} \app \iexp{list}$ such that $\iexp{lseg} \app xsi \app p \app \iexp{null}$, i.e., $p$ is the start pointer of a list segment related to $xsi$, terminated by the $\iexp{null}$ pointer, and $xsi$ and $xs$ are related element-wise as specified by $\iexp{list\_aux}$.

\subsubsection{Non-destructive List Access using \iexp{foldl}}\label{sec:non-destructive-list-access-using-fold}

\refsec{sec:ownership-in-isabelle-llvm} describes a particular challenge when working with lists in LLVM that was not present with the old Imperative-HOL backend:
Lists are not pure in Isabelle-LLVM meaning that fundamental list operations, like reading the head of a list, destroy the original list.

As an example, consider the following recursive function for summing up the elements of a list:
\isabellecodeextern[linerange=45-47,label=algo:llvm-sum,caption={
			Recursive summation over a list, destroying the list in the process.
		}]{isabelle-code/Lists.thy}

A refined version of $\iexp{sum}$ on $\iexp{llM}$-level is shown in \refalgo{algo:llvm-sum-refined}.
\isabellecodeextern[linerange=99-118,label=algo:llvm-sum-refined,caption={
			Refined $\iexp{llM}$-level implementation of the sum function from \refalgo{algo:llvm-sum}.
		}]{isabelle-code/Lists.thy}
$\iexp{os\_is\_empty} \dbcolon \tv{b} \app \iexp{node} \app \iexp{ptr} \rightarrow \iexp{bool} \app \iexp{llM}$ is an emptiness check for lists, $\iexp{os\_pop} \dbcolon \tv{b} \app \iexp{node} \app \iexp{ptr} \rightarrow (\tv{b} \times \tv{b} \app \iexp{node} \app \iexp{ptr}) \app \iexp{llM}$ destructures a given list into its head and tail\footnote{Both $\iexp{os\_is\_empty}$ and $\iexp{os\_pop}$ are defined in theory \isaname{Isabelle_LLVM.LLVM_DS_Open_List}.} and $\iexp{ll\_add} \dbcolon 64 \app \iexp{word} \rightarrow 64 \app \iexp{word} \rightarrow 64 \app \iexp{word} \app \iexp{llM}$ adds two 64-bit integers.
$\iexp{un64.cl\_free}$ at the end of the function frees the list $xsi$ which, at this point, is empty as it is the result of reaching the base case with $\iexp{os\_is\_empty} \app xsi = \iexp{True}$.
Note that for simplicity, I ignore the possibility of an overflow in the addition which constricts the refinement to non-overflowing cases, adding a precondition to the actual refinement lemma.

For $\iexp{os\_pop}$ in particular it holds that
\begin{gather*}
	\{(\iexp{ls\_assn} \app A) \app xs \app xsi\} \app
	(\iexp{os\_pop} \app xsi) \app
	\{\lambda (hi,ti). \app A \app (\iexp{hd} \app xs) \app hi \app \ast \app (\iexp{ls\_assn} \app A) \app (\iexp{tl} \app xs) \app ti\}
\end{gather*}
where the functions $\iexp{hd} \dbcolon \tv{a} \app \iexp{list} \rightarrow \tv{a}$ and $\iexp{tl} \dbcolon \tv{a} \app \iexp{list} \rightarrow \tv{a} \app \iexp{list}$ return the head (first element of the list) and tail (the list without the first element) of a list respectively.
The Hoare-triple implies that the original $xsi$ is destroyed after executing $\iexp{os\_pop} \app xsi$.
Consequently, $\iexp{sum\_impl}$ destroys the given list $xsi$.
If it did not, there would simultaneously exist two pointers into the list, one owned by the caller of $\iexp{sum\_impl}$, one owned by $\iexp{sum\_impl}$, which is forbidden in the separation logic.

If, from the caller's perspective, the original list is required to be kept intact, a straightforward solution is to create a deep copy of a list and then call $\iexp{sum\_impl}$ on the list copy.
Assuming the contained elements support copying, i.e. instantiate $\iexp{copyable\_assn}$, a deep-copy operation $\iexp{ls\_copy} \dbcolon \tv{b} \app \iexp{node} \app \iexp{ptr} \rightarrow \tv{b} \app \iexp{node} \app \iexp{ptr} \app \iexp{llM}$ can easily be implemented by a recursive walk on the list, copying each element into a new list.\footnote{cf. function $\iexp{cl\_copy}$ in theory \isaname{LLVM_DS_Copying_List}.}
Conceptually however, $\iexp{sum\_impl}$ only reads from the given list and does not modify it since the contained elements (64-bit machine words refining natural numbers) are pure and can trivially be cloned for use in the addition $\iexp{ll\_add}$ without necessarily destroying the original list element.
Creating a deep copy is wasteful in this case.

To address this issue and provide an option to implement read-only operations on lists, I implement a refinement target for the HOL $\iexp{foldl} \dbcolon (\tv{a} \rightarrow \tv{b} \rightarrow \tv{a}) \rightarrow \tv{a} \rightarrow \tv{b} \app \iexp{list} \rightarrow \tv{a}$ function.
\isabellecodeextern[linerange=51-56,label=algo:llvm-fold,caption={
			$\iexp{llM}$ level $\iexp{foldl}$ implementation.
		}]{isabelle-code/Lists.thy}
A simplified version is given in \refalgo{algo:llvm-fold}\footnote{The actual function $\iexp{cl\_fold}$ is defined in theory \isaname{LLVM_DS_Copying_List} and uses $\iexp{MMonad.REC}$ for recursion.}.
$\iexp{ll\_load} \dbcolon \tv{a} \app \iexp{ptr} \rightarrow \tv{a}$ is a pointer dereference in $\iexp{llM}$ programs.

On $\iexp{ll\_fold}$, I prove a lemma
\begin{gather*}
	\{A \app a \app ai \app \ast B \app b \app bi\} \app
	(fi \app ai \app bi) \app
	\{\lambda r. A \app (f \app a \app b) \app r \app \ast B \app b \app bi\} \Rightarrow \\
	\{A \app a \app ai \app \ast (\iexp{ls\_assn} \app B) \app bs \app bsi\} \\
	(\iexp{ll\_fold} \app fi \app ai \app bsi)\\
	\{\lambda r. A \app (\iexp{foldl} \app f \app a \app bs) \app r \app \ast (\iexp{ls\_assn} B) \app bs \app bsi\}
\end{gather*}
which can be read as follows: For two given refinement assertions $A \dbcolon \tv{a} \rightarrow \tv{ai} \rightarrow \iexp{assn}, B \dbcolon \tv{b} \rightarrow \tv{bi} \rightarrow \iexp{assn}$, if $fi \dbcolon \tv{ai} \rightarrow \tv{bi} \rightarrow \tv{bi} \app \iexp{llM}$ refines a function $f \dbcolon \tv{a} \rightarrow \tv{b} \rightarrow \tv{a}$ such that the second argument of type $\tv{bi}$ is kept intact, then $\iexp{ll\_fold} \app fi \dbcolon \tv{ai} \rightarrow \tv{bi} \app \iexp{node} \app \iexp{ptr} \rightarrow \tv{ai} \app \iexp{llM}$ refines $\iexp{foldl} \app f \dbcolon \tv{a} \rightarrow \tv{b} \app \iexp{list} \rightarrow \tv{a}$ such that the given list is kept intact.

With this lemma, it is possible to reformulate the sum implementation as shown in \refalgo{algo:sum-alt}.
\isabellecodeextern[linerange=59-60,label=algo:sum-alt,caption={
			Alternative, equivalent reformulation of \iexp{sum}, using \iexp{foldl}.
		}]{isabelle-code/Lists.thy}
It is straightforward to prove $\iexp{sum'} = \iexp{sum}$ and a refinement lemma
\begin{gather*}
	\{(\iexp{ls\_assn} \app \iexp{un64\_assn}) \app xs \app xsi \app \ast \uparrow((\iexp{sum'} \app (+) \app 0 \app xs) \le 2^{64}-1)\} \\
	(\iexp{ll\_fold} \app \iexp{ll\_add} \app \iexp{0x0} \app xsi) \\
	\{\lambda r. \iexp{un64\_assn} \app (\iexp{sum'} \app (+) \app 0 \app xs) \app r \app \ast (\iexp{ls\_assn} \app \iexp{un64\_assn}) \app xs \app xsi\}.
\end{gather*}
Note that in this version, the original list $xsi$ is kept intact and not destroyed, with no initial deep copy of $xsi$ being required.

\subsubsection{Interleaving Fold over two Lists}\label{sec:interleaving-fold}

The $\iexp{ll\_fold}$ implementation can be used to avoid deep copying lists when traversing a single list, as discussed in \refsec{sec:non-destructive-list-access-using-fold}.
Multiple functions in Pastèque however traverse through two lists simultaneously.
As an example, consider the addition function $\iexp{add\_poly}$ for two polynomials, shown in \refalgo{algo:poly-add}, where $\iexp{term\_order\_rel} \dbcolon (\iexp{string} \app \iexp{list} \times \iexp{string} \app \iexp{list}) \app \iexp{set}$ defines a lexicographic order on lists of strings.
\isabellecodeextern[linerange=198-215,label=algo:poly-add,caption={
			Addition Function for two given polynomials.
		}]{isabelle-code/Lists.thy}

$\iexp{add\_poly}$ has a similar issue as $\iexp{sum}$ from \refsec{sec:non-destructive-list-access-using-fold}:
Refining $\iexp{add\_poly}$ as presented to $\iexp{llM}$-level would lead to destructuring the lists by use of $\iexp{os\_pop}$, meaning that $\iexp{add\_poly}$ would destroy the given lists even though conceptually it only reads from the lists and does not modify them.
As the polynomials in the addition are potentially used in further operations, a straightforward refinement of $\iexp{add\_poly}$ requires cloning the two input polynomials.
Also, $\iexp{ll\_fold}$ does not help in this case as it can only traverse a single list.

To obtain a way to non-destructively traverse two lists, I define an \textit{interleaving fold} function as shown in \refalgo{algo:interleaving-fold}, where $\iexp{direction} = \iexp{LEFT} \mid \iexp{RIGHT} \mid \iexp{BOTH} \mid \iexp{STOP}$.
\isabellecodeextern[linerange=130-144,label=algo:interleaving-fold,caption={
			Interleaving fold operation to enable read-only traversal through two lists.
		}]{isabelle-code/Lists.thy}
$\iexp{ifoldl}$ constructs an accumulated value of type $\tv{a}$ by traversing two lists of types $\tv{b} \app \iexp{list}$ and $\tv{c} \app \iexp{list}$.
In each step, the second argument of $\iexp{ifoldl}$, a function $\iexp{dec} \dbcolon \tv{b} \rightarrow \tv{c} \rightarrow \iexp{direction}$, is used to decide in which of the two lists the traversal should continue:
If $\iexp{dec} \app b \app c = \iexp{LEFT}$, for the current elements $b \dbcolon \tv{b}$ and $c \dbcolon \tv{c}$, then $\iexp{ifoldl}$ advances in the first list, while in the second list, it stays at the current element $c$.
Naturally, $\iexp{dec} \app b \app c = \iexp{RIGHT}$ is the inverse case.
For $\iexp{dec} \app b \app c = \iexp{BOTH}$, $\iexp{ifoldl}$ advances in both lists, while $\iexp{dec} \app b \app c = \iexp{STOP}$ allows for an early exit.
The first argument $f \dbcolon \tv{a} \rightarrow \tv{b} \rightarrow \tv{c} \rightarrow \iexp{direction} \rightarrow \tv{a}$ is a generalization of the inner $f \dbcolon \tv{a} \rightarrow \tv{b} \rightarrow \tv{a}$ in the regular $\iexp{foldl}$, which allows updating the accumulator of type $\tv{a}$ based on the current list elements of types $\tv{b}$ and $\tv{c}$ and can also consider the chosen direction, resulting from $\iexp{dec} \app b \app c$.
As it is likely that $\iexp{ifoldl}$ finishes traversal of one list, while the other list is not yet traversed completely, the arguments $f1 \dbcolon \tv{a} \rightarrow \tv{b} \rightarrow \tv{a}$ and $f2 \dbcolon \tv{a} \rightarrow \tv{c} \rightarrow \tv{a}$ allow for finishing the traversal of the unfinished list using the regular $\iexp{foldl}$ starting with the current accumulator.

With $\iexp{ifoldl}$ it is possible to reimplement $\iexp{add\_poly}$ in a non-destructive way.
To do so, I define a decision function $\iexp{add\_dec}$ shown in \refalgo{algo:add-dec}.

Note how $\iexp{add\_dec}$ models the original three cases in \refalgo{algo:poly-add}.
The inner function for the accumulator update is given by $\iexp{add\_update}$ shown in \refalgo{algo:add-update}, modeling the bodies of the three cases in $\iexp{add\_poly}$.

Once the interleaving traversal has reached the end of one of the lists, the other list must be appended to the accumulator.
This corresponds to the base cases in \refalgo{algo:poly-add} with inputs $p \app \iexp{[\app]}$ and $\iexp{[\app]} \app q$ respectively.

I then prove that
\begin{align*}
	\iexp{add\_poly} \app p \app q = \iexp{ifoldl} & \app \iexp{add\_update} \app \iexp{add\_dec} \app \iexp{add\_copy\_remainder} \\
	                                               & \app \iexp{add\_copy\_remainder} \app \iexp{[\app]} \app p \app q
\end{align*}
to obtain an $\iexp{ifoldl}$-based alternative addition implementation.

For the actual refinement down to $\iexp{llM}$-level, I prove a lemma for a refinement target $\iexp{ll\_ifoldl}$ analogously to $\iexp{ll\_fold}$ in \refsec{sec:non-destructive-list-access-using-fold}:
\begin{align*}
	 & \{A \app a \app ai \app \ast B \app b \app bi \app \ast C \app c \app ci \app \ast \iexp{dir\_assn} \app d \app di\}                                                   \\
	 & \hcont{\{A \app a \app ai \app \ast} (fi \app ai \app bi \app ci \app di)                                                                                              \\
	 & \hcont{\{A \app a \app ai \app \ast} \{\lambda r. A \app (f \app a \app b \app c \app d) \app r \app \ast B \app b \app bi \app \ast C \app c \app ci\} \Rightarrow    \\[0.5em]
	 & \{B \app b \app bi \app \ast C \app c \app ci\} \app (deci \app bi \app ci)                                                                                            \\
	 & \hcont{\{B \app b \app bi \app \ast} \{\lambda r. \iexp{dir\_assn} \app (dec \app b \app c) \app r \app \ast B \app b \app bi \app \ast C \app c \app ci\} \Rightarrow \\[0.5em]
	 & \{A \app a \app ai \app \ast B \app b \app bi\} \app (f_1i \app ai \app bi) \app
	\{\lambda r. A \app (f_1 \app a \app b) \app r \app \ast B \app b \app bi\} \Rightarrow                                                                                   \\[0.5em]
	 & \{A \app a \app ai \app \ast C \app c \app ci\} \app (f_2i \app ai \app ci) \app
	\{\lambda r. A \app (f_2 \app a \app c) \app r \app \ast C \app c \app ci\} \Rightarrow                                                                                   \\[0.5em]
	 & \{A \app acc \app acci \app \ast (\iexp{ls\_assn} \app B) \app bs \app bsi \app \ast (\iexp{ls\_assn} \app C) \app cs \app csi\}                                       \\
	 & \hcont{\{A \app acc \app acci \app \ast} (\iexp{ll\_ifoldl} \app fi \app deci \app f_1i \app f_2i \app acci \app bsi \app csi)                                         \\
	 & \hcont{\{A \app acc \app acci \app \ast} \{\lambda r. A \app (\iexp{ifoldl} \app f \app dec \app f_1 \app f_2 \app acc \app bs \app cs) \app r                         \\
	 & \hcont{\{A \app acc \app acci \app \ast \{\lambda r.} \ast (\iexp{ls\_assn} \app B) \app bs \app bsi \app \ast (\iexp{ls\_assn} \app C) \app cs \app csi\}
\end{align*}
where $\iexp{dir\_assn} \dbcolon \iexp{direction} \rightarrow 8 \app \iexp{word} \rightarrow \iexp{assn}$ is a refinement assertion for the $\iexp{direction}$ type, encoding each of the four constructors $\iexp{LEFT}, \iexp{RIGHT}, \iexp{BOTH}, \iexp{STOP}$ by a number $\iexp{0}-\iexp{3}$.
The lemma can be read as follows: Assuming the following preconditions are fulfilled:
\begin{enumerate}
	\item $f \dbcolon \tv{a} \rightarrow \tv{b} \rightarrow \tv{c} \rightarrow \iexp{direction} \rightarrow \tv{a}$ is refined by $fi \dbcolon \tv{ai} \rightarrow \tv{bi} \rightarrow \tv{ci} \rightarrow 8 \app \iexp{word} \rightarrow \tv{ai}$, such that the second argument $bi \dbcolon \tv{bi}$ and third argument $ci \dbcolon \tv{ci}$ are kept intact, which models a read-only access to the input lists.
	\item The decision function $dec \dbcolon \tv{b} \rightarrow \tv{c} \rightarrow \iexp{direction}$ is refined by $\iexp{deci} \dbcolon \tv{bi} \rightarrow \tv{ci} \rightarrow 8 \app \iexp{word}$ with the arguments being kept intact.
	\item Functions $f_1$ and $f_2$ are refined by $f_1i$ and $f_2i$ such that the respective list elements are kept intact.
\end{enumerate}
Then, $\iexp{ll\_ifoldl} \app fi \app deci \app f_1i \app f_2i \app acci \app bsi \app csi$ refines $\iexp{ifoldl} \app f \app dec \app f_1 \app f_2 \app acc \app bs \app cs$, with $acci, bsi, csi$ being the concrete accumulator and input lists for the abstract accumulator and input lists $acc, bs, cs$, such that the lists $bsi$ and $csi$ are kept intact.

This ultimately allows for implementing a read-only polynomial addition such that the two input polynomials need not be cloned before the addition is performed.

\subsubsection{A Generic Merge Sort Implementation for Lists}\label{sec:generic-merge-sort-for-lists}

As a preprocessing step, Pastèque sorts variables of a term and the terms of a polynomial by a lexicographic order.
The existing merge sort implementation used in Pastèque splits up the lists using the $\iexp{drop} \dbcolon \iexp{nat} \rightarrow \tv{a} \app \iexp{list} \rightarrow \tv{a} \app \iexp{list}$ and $\iexp{take} \dbcolon \iexp{nat} \rightarrow \tv{a} \app \iexp{list} \rightarrow \tv{a} \app \iexp{list}$ functions, which return a prefix and a suffix of a given list with the given length respectively.
$\iexp{take}$ and $\iexp{drop}$ are not implemented for $\iexp{ls\_assn}$.
I therefore implement a generic merge sort algorithm that is designed to work well with $\iexp{ls\_assn}$.

For this subsection, I assume that a refinement assertion $A \dbcolon \tv{a} \rightarrow \tv{b} \rightarrow \iexp{assn}$ instantiates $\iexp{linorder\_assn}$.
In particular, I assume a function $(<) \dbcolon \tv{a} \rightarrow \tv{a} \rightarrow \iexp{bool}$ is defined with a corresponding refinement target $\iexp{alt} \dbcolon \tv{b} \rightarrow \tv{b} \rightarrow \iexp{bool} \app \iexp{llM}$.
On $(<)$, I assume transitivity and totality.

As a first step, the list is split into singleton lists by a function $\iexp{explode} \dbcolon \tv{a} \app \iexp{list} \rightarrow \tv{a} \app \iexp{list} \app \iexp{list}$ with $\iexp{explode} = \iexp{map} \app (\lambda x. \app [x])$.
$\iexp{explode}$ is straightforward to refine by a while-based implementation in $\iexp{nres}$.

Then, a classic merge step merges two sorted lists into one, as shown in \refalgo{algo:merge}.
\isabellecodeextern[linerange=10-20,label=algo:merge,caption={
			Implementation of the merge step of the merge sort algorithm.
		}]{isabelle-code/SortingSimplified.thy}
Using the \inlinecode{refine_vcg} verification condition generator, I then show that
\begin{gather*}
	\iexp{sorted} \app xs \land \iexp{sorted} \app ys \Rightarrow \\
	\iexp{merge} \app xs \app ys \le \iexp{SPEC} \app (\lambda r. \app \iexp{sorted} \app r \land \iexp{mset} \app r = \iexp{mset} \app xs + \iexp{mset} \app ys),
\end{gather*}
where $\iexp{sorted} \dbcolon \tv{a} \app \iexp{list} \rightarrow \iexp{bool}$ evaluates to $\iexp{True}$ iff the given list is sorted.

Starting with the original singleton lists, resulting from $\iexp{explode}$, pairs of lists are merged until a single sorted list is left in a function $\iexp{msort} \dbcolon \tv{a} \app \iexp{list} \rightarrow \tv{a} \app \iexp{list}$.
For $\iexp{msort}$, I then prove correctness by a lemma
\begin{gather*}
	\iexp{msort} \app xs \le \iexp{SPEC} \app (\lambda r. \app \iexp{sorted} \app r \land \iexp{mset} \app r = \iexp{mset} \app xs).
\end{gather*}
Note that in the merge step in \refalgo{algo:merge}, the lesser of $\iexp{x}$ and $\iexp{y}$ is appended to the result list $\iexp{r}$ by $\iexp{r} \app \iexp{@} \app \iexp{[x]}$ or $\iexp{r} \app \iexp {@} \app \iexp{[y]}$ respectively.
Using the list implementation presented in \refsec{sec:refinement-assertion-for-lists}, appending to a list is linear in its length since the append operation must traverse the entire list to get to its last element.
To avoid the linear append operation, I use a separate list implementation which also stores a pointer to the last element directly, allowing for a constant time append operation.

\subsubsection{Extending the Refinement Assertion for Lists}\label{lists-with-tail-pointers}

For the regular linked list, cf. \refsec{sec:refinement-assertion-for-lists}, the refinement target is a pointer $\tv{b} \app \iexp{node} \app \iexp{ptr}$.
The pointer points at the head of the list.
To store a pointer to the last element of a list, the refinement target extends to $\tv{b} \app \iexp{node} \app \iexp{ptr} \times \tv{b} \app \iexp{node} \app \iexp{ptr}$.
The first element still points at the head of the list, while the second element points at the last node.

A refinement assertion that also stores a pointer to the end of the list is given by\footnote{
	like $\iexp{ls\_assn}$ in \refsec{sec:refinement-assertion-for-lists}, the presented $\iexp{lst\_assn}$ is somewhat simplified.
	The actual $\iexp{clt\_assn}$ assertion in \isaname{LLVM_DS_Copying_List} also uses the custom $\iexp{olseg}$ assertion that includes the auxiliary $\iexp{list\_aux}$ ($\iexp{list\_assn}$ in the actual theory \isaname{Isabelle_LLVM.ProtoEOArray}.)
}
\begin{align*}
	\iexp{lst\_assn} \app & A \app xs \app (p,q) =                                   \\
	                      & \begin{cases}
		                        \uparrow(p=\iexp{null}) & \text{, if $xs=[\app]$} \\[1ex]
		                        \begin{aligned}
			 & \exists c\app xsi. \app \iexp{lseg} \app xsi \app p \app q \app \ast \app \iexp{list\_aux} \app A \app (\iexp{butlast} \app xs) \app xsi               \\
			 & \ast \app q \mapsto (\iexp{Node} \app c \app \iexp{null}) \app \ast \app A \app (\iexp{last} \app xs) \app c \app \ast \app \uparrow(p\neq\iexp{null})
		\end{aligned}
		                                                & \text{, otherwise}
	                        \end{cases}
\end{align*}
where $\iexp{butlast} \dbcolon \tv{a} \app \iexp{list} \rightarrow \tv{a} \app \iexp{list}$ returns a list without its last element and $\iexp{last} \dbcolon \tv{a} \app \iexp{list} \rightarrow \tv{a}$ returns the last element from a list.
Note that the first line of the second case is essentially $\iexp{ls\_assn} \app A \app (\iexp{butlast} \app xs) \app p$ with the addition that $q$ is the end of this list segment, while the second line ensures that $q$ points to the last list element $\iexp{Node} \app c \app \iexp{null}$ and that $A \app (\iexp{last} \app xs) \app c$.
Also, $p$ is required to be $\neq \iexp{null}$ for non-empty lists, which is necessary to add since in the first line, $\iexp{butlast} \app xs$ might be the empty list for a singleton $xs=[c]$.

The construction of $\iexp{lst\_assn} \dbcolon (\tv{a} \rightarrow \tv{b} \rightarrow \iexp{assn}) \rightarrow \tv{a} \app \iexp{list} \rightarrow (\tv{b} \app \iexp{node} \app \iexp{ptr} \times \tv{b} \app \iexp{node} \app \iexp{ptr}) \rightarrow \iexp{assn}$ allows for constant-time append and concatenation operations.
Conversion from a list with tail pointer to a list without it is also constant time, since it simply amounts to dropping the tail pointer.
Conversion from a list without tail pointer to a list with tail pointer however is linear in the list's length.

\subsection{Partial Maps}\label{sec:partial-maps}

Pastèque is given the enumerated input polynomials as input, as described in \refsec{sec:methodology_high-level-representation-of-polynomials}.
On HOL-level, this list of polynomials is modeled by a partial map of type $\iexp{nat} \rightharpoonup \iexp{polynomial}$.
A proof step may reference polynomials for use in arithmetic operations and may add new polynomials to the map.
Adding a new polynomial with an existing index is treated as overwriting the existing polynomial.

The high-level datatype indicates three requirements for its low-level refinement target:
\begin{enumerate}
	\item The map must be able to hold values whose refinement assertions are not pure, while indices can be refined by 64-bit machine words. Note that this adds the constraint that the number of stored polynomials must not exceed the largest representable index of $2^{63}-1$ (indices use signed integers)\footnote{Due to the resizing implementation, the actual upper bound is $2^{63}-2$. This is discussed in \refsec{sec:a-new-error-path}}.
	\item Lookup and update should have $\mathcal{O}(1)$ time complexity.
	\item The map must be able to represent empty slots, i.e. it might be that Pastèque references an index at which no polynomial is stored.
	      This would result in a runtime error, but the state where a slot is inhabited must still be representable.
	      More concretely, the cells in the map must refine Isabelle/HOL's option type.
\end{enumerate}
For the lookup operation, there are two options to choose from:
Retrieving an element could either transfer ownership of the element to the caller, leaving the slot empty, or the contained element can be copied out of the map.
I initially chose the latter by requiring contained elements to instantiate $\iexp{copyable\_assn}$, a later added optimization avoids this copy from the callers side which is discussed in \ref{sec:avoiding-polynomial-deep-copies}.

The linked lists in \refsec{sec:lists-with-tail-pointers} directly refine Isabelle/HOL's list type.
For the partial maps, the high-level type to refine is $\iexp{nat} \rightharpoonup \iexp{polynomial}$ which is a type synonym for $\iexp{nat} \rightarrow \tv{a} \app \iexp{option}$.
I choose a two-step refinement approach here; I first refine $\iexp{nat} \rightarrow \tv{a} \app \iexp{option}$ by $\tv{a} \app \iexp{option} \app \iexp{list}$ on $\iexp{nres}$ level, then I define a concrete LLVM-level refinement of $\tv{a} \app \iexp{option} \app \iexp{list}$ down to $\iexp{llM}$ level.

\subsubsection{High-Level Refinement of Partial Map by List of Optionals}\label{sec:partial-map-by-list-of-optionals}

A list of optionals $\tv{a} \app \iexp{option} \app \iexp{list}$ is associated to a map $\iexp{nat} \rightarrow \tv{a} \app \iexp{option}$ by an abstraction function $\iexp{opt\_list\_}\alpha \dbcolon \tv{a} \app \iexp{option} \app \iexp{list} \rightarrow \iexp{nat} \rightarrow \tv{a}$ where
\begin{gather*}
	\iexp{opt\_list\_}\alpha \app ol = \lambda \app n.
	\begin{cases}
		ol \app \iexp{!} \app n & \text{, if $n < \iexp{length} \app ol$} \\
		\iexp{None}             & \text{, otherwise}
	\end{cases}
\end{gather*}
so that $\iexp{opt\_list\_}\alpha$ yields a partial map for a given list of optionals.
Similarly to the refinement relations discussed in \ref{sec:multiple-precision-integers}, a refinement relation between lists of optionals and partial maps is given by $\iexp{opt\_list\_map\_rel} \dbcolon (\tv{a} \app \iexp{option} \app \iexp{list} \times \iexp{nat} \rightarrow \tv{a} \app \iexp{option}) \app \iexp{set}$ where
\begin{gather*}
	(ol,m) \in \iexp{opt\_list\_map\_rel} \Leftrightarrow m = \iexp{opt\_list\_}\alpha \app ol
\end{gather*}
with the trivial invariant $\lambda \_. \app \iexp{True}$

I implement all required operations from Isabelle-LLVM's map interface\footnote{cf. theory \isaname{Isabelle_LLVM.IICF_Map}.} on lists of optionals.
I discuss lookup and update here, the other functions are implemented in a similar manner.\footnote{cf. theory \isaname{LLVM_DS_Partial_Map}.}
\begin{itemize}
	\item The lookup function, $\iexp{opt\_list\_lookup} \dbcolon \iexp{nat} \rightarrow \tv{a} \app \iexp{option} \app \iexp{list}$ for a given key $k$ and a list of optionals $ol$ is implemented by
	      \begin{gather*}
		      \iexp{opt\_list\_lookup} \app k \app ol =
		      \begin{cases}
			      ol \app \iexp{!} \app k & \text{, if $k < \iexp{length} \app ol$} \\
			      \iexp{None}             & \text{, otherwise}
		      \end{cases}
	      \end{gather*}
	      In the next section, the list is eventually refined by an array, so $ol \app \iexp{!} \app k$ has $\mathcal{O}(1)$ runtime.
	\item The update function, $\iexp{opt\_list\_update} \dbcolon \iexp{nat} \rightarrow \tv{a} \rightarrow \tv{a} \app \iexp{option} \app \iexp{list}$, for given key $k$, value $v$ and list $ol$ of optionals is implemented by
	      \begin{gather*}
		      \iexp{opt\_list\_update} \app k \app v \app ol = (ol \app \iexp{@} \app \iexp{None}^{(k + 1 - \iexp{length} \app ol)})[k:=v]
	      \end{gather*}
	      where $\iexp{@}$ concatenates two lists, $\iexp{None}^x$ denotes the list $[\iexp{None},\dots,\iexp{None}]$ containing $\iexp{None}$ $x$ times, and $l[i:=x]$ denotes list $l$ with the element at position $i$ being updated to $x$.\\
	      This implementation introduces some further requirements for the low-level implementation: The array must be growable, and newly allocated slots must be initialized with (the refinement target of) $\iexp{None}$.
\end{itemize}

For each implemented operation I then prove its correctness.
For $\iexp{opt\_list\_lookup}$, correctness is proved by a lemma\footnote{The actual lemmas in theory \isaname{LLVM_DS_Partial_Map} are given in "fref" notation with operations lifted into $\iexp{nres}$. For the thesis, I use a simplified formulation which implies the fref notation.}
\begin{gather*}
	m = \iexp{opt\_list\_}\alpha \app ol \Rightarrow
	\iexp{opt\_list\_lookup} \app k \app ol = m \app k
\end{gather*}
For $\iexp{opt\_list\_update}$, correctness is given by
\begin{gather*}
	m = \iexp{opt\_list\_}\alpha \app ol \Rightarrow
	\iexp{opt\_list\_}\alpha \app (\iexp{opt\_list\_update} \app k \app v \app ol) = m(k\mapsto v)
\end{gather*}
where $m(k \mapsto v)$ is map $m$ with $k$ mapped to $v$.

\subsubsection{Low-Level Refinement of Lists of Optionals}\label{sec:low-level-refinement-of-lists-of-optionals}

The lists of optionals from \refsec{sec:partial-map-by-list-of-optionals} need a concrete refinement target in $\iexp{llM}$.
Isabelle-LLVM defines a refinement target for optionals through the locale $\iexp{dflt\_option\_private}$\footnote{defined in theory \isaname{Isabelle_LLVM.Sepref_HOL_Bindings}.}, which requires the contained elements to provide a check for whether they are initialized.
A type's default value $\iexp{dflt}$ represents uninitialized values.
When allocating an array for instance, all slots have value $\iexp{dflt}$ initially\footnote{cf. lemma $\iexp{narray\_new\_rule\_snat}$ in theory \isaname{Isabelle_LLVM.LLVM_DS_NArray}.}.
To refine optionals, a refinement assertion $A \dbcolon \tv{a} \rightarrow \tv{b} \rightarrow \iexp{assn}$ has to provide a function $\iexp{is\_dflt} \dbcolon \tv{b} \rightarrow \iexp{bool} \app \iexp{llM}$.
With $\iexp{is\_dflt}$, $A$ can instantiate $\iexp{dflt\_option\_private}$, and obtain $A\iexp{.option\_assn} \dbcolon \tv{a} \app \iexp{option} \rightarrow \tv{b} \rightarrow \iexp{assn}$ which is a refinement assertion for optionals of type $\tv{a} \app \iexp{option}$.

For pointers in particular, it holds that $\iexp{dflt} = \iexp{null}$ and it is possible to check if a pointer $p$ is $\iexp{null}$ using Isabelle-LLVM's $\iexp{ll\_ptrcmp\_eq}$\footnote{Defined in theory \isaname{Isabelle_LLVM.LLVM_Shallow}.}.
I therefore define a refinement assertion $\iexp{box\_assn} \dbcolon (\tv{a} \rightarrow \tv{b} \rightarrow \iexp{assn}) \rightarrow \tv{a} \rightarrow \tv{b} \app \iexp{ptr} \rightarrow \iexp{assn}$ that simply wraps arbitrary data types in a pointer by
\begin{gather*}
	\iexp{box\_assn} \app A = \lambda a \app p. \app \exists ai. \app A \app a \app ai \app \ast p\mapsto ai
\end{gather*}
\todo{why do we need box assn?}
where $A \dbcolon \tv{a} \rightarrow \tv{b} \rightarrow \iexp{assn}$ is an existing refinement assertion.
It is then straightforward to use $\iexp{box\_assn}$ as a generic implementation for optionals, where for $a \dbcolon \tv{a}$, $\iexp{Some} \app a$ with $A \app a \app ai$ is refined by a pointer $p \dbcolon \tv{b} \app \iexp{ptr}$ with $p \mapsto ai$ and $\iexp{None}$ is refined by the null pointer.
$\iexp{box\_assn} \app A$ can then be used to instantiate $\iexp{dflt\_option\_private}$ even if the refinement assertion $A$ itself does not define an $\iexp{is\_dflt}$ check.
For the remainder of this subsection, I assume $A \dbcolon \tv{a} \rightarrow \tv{b} \rightarrow \iexp{assn}$ to be a refinement assertion that instantiates $\iexp{dflt\_option\_private}$ (which in the Pastèque implementation is always achieved through the $\iexp{box\_assn}$ wrapper).

I refine the outer list of the high level $\tv{a} \app \iexp{option} \app \iexp{list}$ using a variation of Isabelle-LLVM's $\iexp{arl\_assn}$\footnote{Defined in theory \isaname{Isabelle_LLVM.LLVM_DS_Array_List}.}.
$\iexp{arl\_assn}$ refines lists by arrays and stores the array's length and capacity (which might be greater than the length).

The variation of $\iexp{arl\_assn}$ I use is defined by $\iexp{iarl\_assn} \dbcolon \tv{a} \app \iexp{list} \rightarrow (64 \app \iexp{word} \app \times \app 64 \app \iexp{word} \app \times \app \tv{a} \app \iexp{ptr}) \rightarrow \iexp{assn}$ as follows:\footnote{The notation given here is slightly simplified, the actual assertion is defined in theory \isaname{LLVM_DS_Partial_Map}.}
\begin{align*}
	\iexp{iarl\_assn}   & \app xs \app (li,ci,ai) =                                                                                                                                     \\
	\exists c \app xs'. & \iexp{sn64\_assn} \app (\iexp{length} \app xs) \app li                                                                                                        \\
	                    & \ast \app \iexp{sn64\_assn} \app c \app ci                                                                                                                    \\
	                    & \ast \app \iexp{narray\_assn} \app xs' \app ai                                                                                                                \\
	                    & \ast \app \uparrow(\iexp{length} \app xs \leq c \land c = \iexp{length} \app xs' \land xs' = xs \app \iexp{@} \app \iexp{dflt}^{(c - \iexp{length} \app xs)})
\end{align*}
where $\iexp{narray\_assn} \dbcolon \tv{a} \app \iexp{list} \rightarrow \tv{a} \app \iexp{ptr} \rightarrow \iexp{assn}$ is Isabelle-LLVM's existing refinement assertion for refining lists by arrays and $\iexp{sn64\_assn} \dbcolon \iexp{nat} \rightarrow 64 \app \iexp{word} \rightarrow \iexp{assn}$ is another existing refinement assertion for refinement of natural numbers by 64-bit machine words (which are interpreted as signed numbers).
$li \dbcolon 64 \app \iexp{word}$ is the array's length, $ci \dbcolon 64 \app \iexp{word}$ is the allocated capacity and $ai \dbcolon \tv{a} \app \iexp{ptr}$ is a pointer to the actual array.
Note that $xs' \dbcolon \tv{a} \app \iexp{list}$ is an auxiliary list that allows reasoning about the allocated space exceeding the array's length.

There are only two differences, compared to the original $\iexp{arl\_assn}$; firstly, the width of length and capacity is fixed to 64 bits.
This makes proofs simpler but makes the implementation less generic, compared to the original $\iexp{arl\_assn}$ for which the bit-width is generic (with a lower bound of 5).
Secondly, $\iexp{iarl\_assn}$ also explicitly asserts that the allocated cells beyond the current length are initialized with $\iexp{dflt}$.
Allocations in Isabelle-LLVM are done through a c-function \inlinecode{isabelle_llvm_calloc} which is a wrapper around \iexp{calloc} which ensures that allocated data is zero-initialized.
Since all allocations go through \inlinecode{isabelle_llvm_calloc}, all arrays in Isabelle-LLVM are initialized with $\iexp{dflt}$, but $\iexp{arl\_assn}$ does not carry this information.
For the purpose of carrying the option type, given by $\iexp{box\_assn}$, it is required that newly allocated space explicitly has value $\iexp{dflt}$, which would be impossible to prove (despite being true) if $\iexp{arl\_assn}$ was used.
As $\iexp{iarl\_assn}$ only extends $\iexp{arl\_assn}$ by information required for proofs, but otherwise uses the same underlying representation, operations already defined on $\iexp{arl\_assn}$ (in particular accessing or updating elements and initializing or resizing the array) can be reused and corresponding correctness proofs carry over to $\iexp{iarl\_assn}$ easily.

To finally obtain a refinement target for lists of optionals, I define $\iexp{pmap\_assn} \dbcolon \tv{a} \app \iexp{option} \app \iexp{list} \rightarrow (64 \app \iexp{word} \app \times \app 64 \app \iexp{word} \app \times \app \tv{b} \app \iexp{ptr}) \rightarrow \iexp{assn}$ as follows
\begin{gather*}
	\iexp{pmap\_assn} = \lambda xs \app p. \app \exists xsi. \app \iexp{iarl\_assn} \app xsi \app p \app \ast \app (\iexp{list\_aux} \app A\iexp{.option\_assn}) \app xs \app xsi
\end{gather*}
This uses the auxiliary $\iexp{list\_aux}$ assertion as defined in \refsec{sec:refinement-assertion-for-lists}.

All operations from the high-level list of optionals implementation are then implemented on $\iexp{llM}$ level.
\isabellecodeextern[linerange=379-392,label=algo:pmap_update-implementation,caption={
			Implementation of the update function on partial maps at $\iexp{llM}$ level (actual Isabelle source code).
		}]{isabelle/IsaFoL-Pasteque-LLVM/PAC_Checker_LLVM/LLVM_DS_Partial_Map.thy}
As an example, the update function is implemented as shown in \refalgo{algo:pmap_update-implementation}:
$\iexp{ll\_icmp\_ult} \app \iexp{ki} \app \iexp{l}$ returns the 1-bit machine word $\iexp{0x1}$ (which corresponds to $\iexp{True}$) if the given key $\iexp{ki}$ is less than the length $\iexp{l}$ of the array.
If the given key is allocated already, the previous element at position $\iexp{ki}$ is freed and the new given value is inserted.
If the given key is not yet allocated, the array is grown if needed before the given element is inserted.
Note that $\iexp{arl\_len}$, $\iexp{arl\_nth}$ and $\iexp{arl\_upd}$ are existing functions from Isabelle-LLVM's $\iexp{arl\_assn}$ implementation, while $\iexp{iarl\_resize}$, which grows the array, is part of my $\iexp{iarl\_assn}$ extension.

I then prove a Hoare-triple
\begin{gather*}
	\{\iexp{sn64\_assn} \app k \app ki \app \ast \app A \app a \app ai \app \iexp{pmap\_assn} \app xs \app ai \app \ast \app \uparrow(k + 1 < 2^{63}-1)\} \\
	(\iexp{pmap\_update} \app ki \app vi \app ai)\\
	\{\lambda r. \app \iexp{pmap\_assn} \app (\iexp{opt\_list\_update} \app k \app v \app xs) \app r\}
\end{gather*}
The triple can be read as follows:
If $ki \dbcolon 64 \app \iexp{word}$ refines a key $k \dbcolon \iexp{nat}$, which fits into a signed 64-bit integer, $ai \dbcolon \tv{b}$ refines $a \dbcolon \tv{a}$ (as specified by refinement assertion $A$) and $ai \dbcolon 64 \app \iexp{word} \times 64 \app \iexp{word} \times \tv{b} \app \iexp{ptr}$ (which is an $\iexp{llM}$ level array) refines $xs \dbcolon \tv{a} \app \iexp{option} \app \iexp{list}$ (as specified by $\iexp{pmap\_assn}$), then, after executing $\iexp{pmap\_update} \app ki \app vi \app ai$, the result refines the result of the high-level implementation $\iexp{opt\_list\_update} \app k \app v \app xs$.
Note that the array takes ownership of the given value, so if the caller wants to keep the value, they must first copy it.

Through this Hoare-triple and the correctness proof of $\iexp{opt\_list\_update}$ in \refsec{sec:partial-map-by-list-of-optionals}, I define a refinement chain $\iexp{pmap\_update} \rightsquigarrow \iexp{opt\_list\_update} \rightsquigarrow (\lambda k \app v \app m. \app m(k\mapsto v))$ which is then picked up by sepref for each map update operation in the high-level Pastèque implementation.

Other operations on the maps are implemented in a similar manner and also have a corresponding Hoare-triple for proving refinement of the higher-level list of optionals implementation.
For the lookup function, I choose to require $A$ to instantiate $\iexp{copyable\_assn}$ such that retrieved elements are copied out of the array while the array keeps ownership of the original elements.
For Pastèque, I had originally considered this to be a reasonable choice as a stored polynomial might be retrieved multiple times.
However, I later decided to avoid this copy through a workaround which is described in \ref{sec:avoiding-polynomial-deep-copies}.

\subsection{Hashsets}\label{sec:hashsets}

Throughout execution, Pastèque keeps a set $\mathscr{V} \dbcolon \iexp{string} \app \iexp{set}$ to keep track of used variables.
An extension step $\iexp{Ext} \app n \app v \app p$ is only accepted if $v \not\in \mathscr{V}$.
I refine $\mathscr{V}$ by a custom hashset implementation following a two-step refinement process similar to the partial map approach.

\subsubsection{High-level set refinement by nested lists}\label{sec:high-level-hashsets}

For this subsection I assume $A \dbcolon \tv{a} \rightarrow \tv{b} \rightarrow \iexp{assn}$ to be a refinement assertion that instantiates $\iexp{eq\_assn}$ and $\iexp{hashable\_assn}$.
In Pastèque I only use hashsets to store strings, but the implementation is generic and can store any type that supports an equality check and provides a hash function.
For the hash function on strings, I implement a FNV-1a hash with values taken from \cite{noll_fnv}, extending characters to 64-bit integers.

As a first step, I refine the abstract $\tv{a} \app \iexp{set}$ type by the (still abstract) type $\tv{a} \app \iexp{hs\_abs} :\equiv \tv{a} \app \iexp{list} \app \iexp{list} \times \iexp{nat}$.
The inner lists represent the buckets and the natural number represents the number of elements in the hashset which is used to detect when resizing and rehashing should be carried out.
I define an invariant on the abstract hashsets, given by
\begin{align*}
	\iexp{lshs\_invar} \app & (xss,l) := \app xss \neq \iexp{[\app]}                                                                                                                                           \\
	                        & \land (\forall i < \iexp{length} \app xss. \app \forall x \in \iexp{set} \app (xss \app \iexp{!} \app i). \app \iexp{lshs\_bucket\_of} \app (\iexp{length} \app xss) \app x = i)
\end{align*}
where $\iexp{lshs\_bucket\_of} \app n \app x := \iexp{unat} \app (\iexp{ahash} \app x) \app \text{mod} \app n$.
Note that the invariant does not make any statement about $l$, which is a deliberate choice; in principle, the invariant could enforce $l = \iexp{length} \app (\iexp{concat} \app xss)$ (where $\iexp{concat} \dbcolon \tv{a} \app \iexp{list} \app \iexp{list} \rightarrow \tv{a} \app \iexp{list}$ flattens a given nested list) as $l$ is used to track the number of contained elements.
However, adding that requirement to the invariant effectively introduces an upper bound on the contained elements since I refine $l$ by a (signed) 64-bit integer in \refsec{sec:low-level-hashset-implementation} which can only store numbers up to $2^{63}-1$.
Instead, I choose to only use $l$ in the actual implementation to improve efficiency and not make the refinement relation between set and $\tv{a} \app \iexp{hs\_abs}$ depend on $l$.
Consequently, I do not prove anything about the load of the hashset, so for instance $[[1,2,3,4]]$ is a valid refinement of the set $\{1,2,3,4\}$ even though $[[1],[2],[3],[4]]$ would be a more appropriate representation as it allows for constant-time access, compared to the linear time access of $[[1,2,3,4]]$.

I define an abstraction from $\tv{a} \app \iexp{hs\_abs}$ to $\tv{a} \app \iexp{set}$, given by $\iexp{lshs\_}\alpha := \lambda(xss,l). \app \{a. \app \exists b\in\iexp{set} \app xss. \app a \in \iexp{set} \app b\}$, and I obtain a refinement relation $\iexp{lshs\_rel} \dbcolon (\tv{a} \app \iexp{hs\_abs} \times \tv{a} \app \iexp{set}) \app \iexp{set}$ where
\begin{gather*}
	(h,s) \in \iexp{lshs\_rel} \Leftrightarrow s = \iexp{lshs\_}\alpha \app h \land \iexp{lshs\_invar} \app h.
\end{gather*}
Similarly to the initial refinement for partial maps \refsec{sec:partial-map-by-list-of-optionals}, I define the core operations $\iexp{lshs\_insert} \dbcolon \tv{a} \rightarrow \tv{a} \app \iexp{hs\_abs} \rightarrow \tv{a} \app \iexp{hs\_abs}$ and $\iexp{lshs\_member} \dbcolon \tv{a} \rightarrow \tv{a} \app \iexp{hs\_abs} \rightarrow \iexp{bool}$ with corresponding correctness lemmas
\begin{align*}
	(h,s) \in \iexp{lshs\_rel} & \Rightarrow (\iexp{lshs\_insert} \app a \app h, s \cup \{a\}) \in \iexp{lshs\_rel} \text{, and} \\
	(h,s) \in \iexp{lshs\_rel} & \Rightarrow (\iexp{lshs\_member} \app a \app h \Leftrightarrow a \in s)\text{.}
\end{align*}
The $\iexp{lshs\_insert}$ operation also increments the counter of contained elements.

I then define a resizing operation
\begin{gather*}
	\iexp{lshs\_resize} := \lambda n \app (xss, l). \app \iexp{fold} \app \iexp{lshs\_insert} \app (\iexp{concat} \app xss) \app (\iexp{replicate} \app n \app \iexp{[\app]},0)
\end{gather*}
for which I show
\begin{gather*}
	(h,s) \in \iexp{lshs\_rel} \land 0 < n \Rightarrow (\iexp{lshs\_resize} \app n \app h, s) \in \iexp{lshs\_rel},
\end{gather*}
meaning that after resizing, a hashset still contains the same elements as before.

\subsubsection{Low-level Hashset implementation}\label{sec:low-level-hashset-implementation}
To implement hashsets on $\iexp{llM}$ level, I use linked lists to represent the buckets, i.e., the inner lists of $\tv{a} \app \iexp{hs\_abs}$, and I use an array%
\footnote{Concretely, I use $\iexp{nao\_assn}$ from theory \isaname{Isabelle_LLVM.Array_of_Array_List}.} to represent the outer list.
Using an array for the outer list allows for $\mathcal{O}(1)$ access to buckets and is thus the natural choice for hashsets.
The number of elements $l$ in the hashset is refined by a 64-bit signed integer which, as stated in \refsec{sec:high-level-hashsets}, means that $l$ can only store the number of contained elements up to $2^{63}-1$.

The refinement relation for $\iexp{hs\_abs}$ is then defined by
\begin{align*}
	\iexp{hs\_assn} := \lambda (xss,l) \app (ni,ai,li). \app & \iexp{sn64\_assn} \app (\iexp{min} \app l \app (2^{63}-1)) \app li                                           \\
	                                                         & \ast \app \iexp{sn64\_assn} \app (\iexp{length} \app xss) \app ni                                            \\
	                                                         & \ast \app \iexp{nao\_assn} \app (\iexp{ls\_assn} \app A) \app (\lambda x. \app \iexp{None}) \app xss \app ai
\end{align*}
where $\iexp{nao\_assn} \dbcolon (\tv{a} \rightarrow \tv{b} \rightarrow \iexp{assn}) \rightarrow (\iexp{nat} \rightarrow \tv{b} \app \iexp{option}) \rightarrow \tv{a} \app \iexp{list} \rightarrow \tv{b} \app \iexp{ptr} \rightarrow \iexp{assn}$ from Isabelle-LLVM, for a given refinement assertion $A \dbcolon \tv{a} \rightarrow \tv{b} \rightarrow \iexp{assn}$ that specifies refinement of the inner elements, specifies refinement of a given list by an array.
Compared to other refinement assertions for arrays in Isabelle-LLVM, $\iexp{nao\_assn}$ does not require the refinement assertion on the inner elements, $A$, to be pure.

With the hashing function $\iexp{ahash\_impl}$, whose existence is guaranteed by $A$ being required to instantiate $\iexp{hashable\_assn}$, it is straightforward to refine $\iexp{lshs\_bucket\_of}$ and thus $\iexp{lshs\_member}$ to $\iexp{llM}$ level.
For the refinement of the $\iexp{lshs\_insert}$ operation, I also implement automatic resizing and rehashing such that, after inserting a new element, the hashset is resized and rehashed if
\begin{itemize}
	\item The number of buckets $n$ is less than or equal to $\iexp{min} \app (2^{63}-1) \app l$, and
	\item $n$ is strictly less than $n' := \text{if } n < 2^{62} \text{ then } 2n \text{ else } n$.
\end{itemize}
Intuitively, if the load factor is $\ge 1$, then the number of buckets is doubled, but doubling stops once the number of buckets reaches $2^{62}$.

I compose the refinement assertion $\iexp{hs\_assn}$ with the relation $\iexp{lshs\_rel}$ to obtain a refinement chain $\iexp{hs\_assn'} \dbcolon \tv{a} \app \iexp{set} \rightarrow (64 \app \iexp{word} \times \tv{b} \app \iexp{node} \app \iexp{ptr} \app \iexp{ptr} \times 64 \app \iexp{word}) \rightarrow \iexp{assn}$ alongside refinement lemmas.
\begin{align*}
	\{\iexp{hs\_assn'} \app s \app si \app \ast \app A \app a \app ai\} \app
	(\iexp{hs\_member} \app ai \app si) \app
	\{\lambda r. \uparrow(r = (a \in s)) \app \ast \app \iexp{hs\_assn'} \app s \app si\}
\end{align*}
and
\begin{align*}
	\{\iexp{hs\_assn'} \app s \app si \app \ast \app A \app a \app ai\} \app
	(\iexp{hs\_insert} \app ai \app si) \app
	\{\lambda r. \app \iexp{hs\_assn'} \app (s \cup \{a\})\app r\}
\end{align*}
respectively.

\subsection{Hashmaps}\label{sec:hashmaps}

Pastèque implements shared variables to avoid duplication of strings in memory (cf. \refsec{sec:methodology_high-level-representation-of-polynomials}) which requires an implementation of hashmaps as refinement target for the high-level type of partial maps $\iexp{string} \rightharpoonup \iexp{nat}$.
The hashmap implementation combines concepts from the partial map implementation (cf. \refsec{sec:partial-maps}) and the hashset implementation (cf. \refsec{sec:hashsets}), following a two-step refinement approach.

\subsubsection{High-level refinement of partial maps by nested lists}\label{sec:hashmaps-partial-maps-by-nested-lists}
For the remainder of this subsection, I assume $K \dbcolon \tv{k} \rightarrow \tv{ki} \rightarrow \iexp{assn}$ to be a refinement assertion for the keys that instantiates $\iexp{hashable\_assn}$, and $V \dbcolon \tv{v} \rightarrow \tv{vi} \rightarrow \iexp{assn}$ to be a refinement assertion for the values that instantiates $\iexp{copyable\_assn}$.
For the only usage of hashmaps in Pastèque, keys are strings, i.e., $K = \iexp{strl\_assn}$ and values are natural numbers, refined by signed 64-bit integers, i.e., $V = \iexp{si64\_assn}$.

The abstract partial map $\tv{k} \rightharpoonup \tv{v}$ is refined by the (still abstract) type $(\tv{k}, \tv{v}) \app \iexp{hm\_abs} :\equiv (\tv{k} \times \tv{v}) \app \iexp{list} \app \iexp{list} \times \iexp{nat}$ with the inner list representing buckets and the natural number in the outer tuple storing the number of elements in the hashmap.
Other than with the hashsets, the inner lists of $(\tv{k}, \tv{v}) \app \iexp{hm\_abs}$ hold tuples of type $\tv{k} \times \tv{v}$, i.e. each entry stores a key alongside its associated value.
An invariant on the intermediate hashmap representation is given by
\begin{align*}
	\iexp{lshm\_invar} := & \lambda (xss, l). \app xss \neq \iexp{[\app]} \land (\forall i < \iexp{length} \app xss.                                            \\
	                      & \iexp{distinct} (\iexp{map} \app \iexp{fst} (xss \app \iexp{!} \app i)) \land                                                       \\
	                      & \forall (k,v) \in \iexp{set} \app (xss \app \iexp{!} \app i). \app \iexp{lshm\_bucket\_of} \app (\iexp{length} \app xss) \app k = i \\
	                      & )
\end{align*}
where $\iexp{distinct} \dbcolon \tv{a} \app \iexp{list} \rightarrow \iexp{bool}$ returns true iff the given list contains only distinct elements and $\iexp{fst} \dbcolon (\tv{a} \times \tv{b}) \rightarrow \tv{a}$ returns the first element of a given tuple.
$\iexp{lshm\_bucket\_of} \dbcolon \iexp{nat} \rightarrow \tv{k} \rightarrow \iexp{nat}$ is given by $\iexp{lshm\_bucket\_of} \app n \app k = \iexp{unat} \app (\iexp{ahash} \app k) \app \iexp{mod} \app n$, analogously to $\iexp{lshs\_bucket\_of}$ in \refsec{sec:high-level-hashsets}.
An abstraction function $\iexp{lshm\_}\alpha \dbcolon (\tv{k},\tv{v})\app \iexp{hm\_abs} \rightarrow \tv{k} \rightharpoonup \tv{v}$ is given by
\begin{align*}
	\iexp{lshm\_}\alpha := \lambda (xss,l) \app k. \app \iexp{map\_of} \app (xss \app \iexp{!} \app \iexp{lshm\_bucket\_of} \app (\iexp{length} \app xss) \app k) \app k
\end{align*}
where $\iexp{map\_of} \dbcolon (\tv{a} \times \tv{b}) \app \iexp{list} \rightarrow \tv{a} \rightharpoonup \tv{b}$ is the map recursively defined by
\begin{gather*}
	\iexp{map\_of} \app ts =
	\begin{cases}
		\lambda x. \app \iexp{None}            & \text{, if $ts=\iexp{[\app]}$}                  \\
		(\iexp{map\_of} \app ts')(k \mapsto v) & \text{, if $ts=(k,v) \app \iexp{\#} \app ts'$.}
	\end{cases}
\end{gather*}
A refinement relation $\iexp{lshm\_rel} \dbcolon ((\tv{k},\tv{v}) \app \iexp{hm\_abs} \times (\tv{k} \rightharpoonup \tv{v})) \app \iexp{set}$ is given by
\begin{gather*}
	(h,s) \in \iexp{lshm\_rel} \Leftrightarrow s = \iexp{lshm\_}\alpha \app h \land \iexp{lshm\_invar} \app h
\end{gather*}
I then implement the following functions for the abstract hashmaps:
\begin{itemize}
	\item   $\iexp{lshm\_update} \dbcolon \tv{k} \rightarrow \tv{v} \rightarrow (\tv{k},\tv{v}) \app \iexp{hm\_abs} \rightarrow (\tv{k},\tv{v}) \app \iexp{hm\_abs}$ with a correctness lemma
	      \begin{gather*}
		      (h,s) \in \iexp{lshm\_rel} \Rightarrow (\iexp{lshm\_update} \app k \app v \app h, s(k\mapsto v)) \in \iexp{lshm\_rel}
	      \end{gather*}
	      where $\iexp{lshm\_update}$ also increments the element counter, if the given key is not yet present in the hashmap.
	\item   $\iexp{lshm\_contains\_key} \dbcolon \tv{k} \rightarrow (\tv{k},\tv{v}) \app \iexp{hm\_abs} \rightarrow \iexp{bool}$ with a correctness lemma
	      \begin{gather*}
		      (h,s) \in \iexp{lshm\_rel} \Rightarrow (\iexp{lshm\_contains\_key} \app k \app h \Leftrightarrow k \in \iexp{dom} \app s)
	      \end{gather*}
	\item   $\iexp{lshm\_lookup} \dbcolon \tv{k} \rightarrow (\tv{k},\tv{v}) \app \iexp{hm\_abs} \rightarrow \tv{v} \app \iexp{option}$ with a correctness lemma
	      \begin{gather*}
		      (h,s) \in \iexp{lshm\_rel} \Rightarrow \iexp{lshm\_lookup} \app k \app h = s \app k
	      \end{gather*}
\end{itemize}

\subsubsection{Low-level Hashmap implementation}\label{sec:low-level-hashmap-implementation}

As for the hashsets (cf. \refsec{sec:low-level-hashset-implementation}), I use linked lists (cf. \refsec{sec:refinement-assertion-for-lists}) to represent the buckets, i.e., the inner lists of $(\tv{k},\tv{v}) \app \iexp{hm\_abs}$.
For the outer list of buckets I use Isabelle-LLVM's $\iexp{arl\_assn}$ (cf. \refsec{sec:partial-map-by-list-of-optionals}), which provides the resizing machinery required for rehashing.

For abstract entries of type $\tv{k} \times \tv{v}$, I define a refinement assertion\footnote{This presentation is simplified, the actual assertion $\iexp{boxed\_buckets\_assn}$ in theory \isaname{LLVM_DS_Hash_Map} wraps the values in a box.}
\begin{gather*}
	\iexp{entry\_assn} := \lambda (k,v) \app (ki,vi). \app K \app k \app ki \app \ast \app V \app v \app vi
\end{gather*}
which states that for a key-value pair, the assertions $K$ and $V$ hold for the respective tuple element.

Refinement of $(\tv{k},\tv{v}) \app \iexp{hm\_abs}$ is achieved by a refinement assertion
$\iexp{hm\_assn} \dbcolon (\tv{k},\tv{v}) \app \iexp{hm\_abs} \rightarrow ((64 \app \iexp{word} \times 64 \app \iexp{word} \times (\tv{ki} \times \tv{vi}) \app \iexp{node} \app \iexp{ptr}) \times 64 \app \iexp{word}) \rightarrow \iexp{assn}$
given by\footnote{
	This presentation is also simplified, in the actual $\iexp{hm\_assn''}$ assertion in theory \isaname{LLVM_DS_Hash_Map}, the buckets are wrapped in the auxiliary $\iexp{oelem\_assn}$ assertion from theory \isaname{Isabelle_LLVM.ProtoEOArray} to enable reasoning about nonexistent buckets, which is required in particular for proving correct the deep-freeing implementation.
}
\begin{align*}
	\iexp{hm\_assn} := \lambda (xss,l) \app (ali,li). \app \exists bsi. \app
	 & \iexp{arl\_assn} \app bsi \app ali                                                          \\
	 & \ast \app \iexp{list\_aux} \app (\iexp{ls\_assn} \app \iexp{entry\_assn}) \app xss \app bsi \\
	 & \ast \app \iexp{sn64\_assn} \app l \app li
\end{align*}
where $bsi \dbcolon ((\tv{ki} \times \tv{vi}) \app \iexp{node}) \app \iexp{list}$ is an auxiliary list of buckets, $ali \dbcolon 64 \app \iexp{word} \times 64 \app \iexp{word} \times (\tv{ki} \times \tv{vi}) \app \iexp{node} \app \iexp{ptr}$ is the array list holding the bucket pointers and $li \dbcolon 64 \app \iexp{word}$ refines the number of elements $l$.

$\iexp{list\_aux}$, as defined in \refsec{sec:refinement-assertion-for-lists}, relates the auxiliary list $bsi$ element-wise to the abstract buckets $xss$, where each bucket is refined by a linked list of entries.
Unlike $\iexp{hs\_assn}$ in \refsec{sec:low-level-hashset-implementation}, $\iexp{hm\_assn}$ does not saturate the element counter, because $\iexp{lshm\_update}$ already caps the abstract counter at $2^{63}-1$.

Similarly to the preceding sections \refsec{sec:partial-maps} and \refsec{sec:hashmaps}, I refine the intermediate functions $\iexp{lshm\_lookup}$ and $\iexp{lshm\_update}$ to $\iexp{llM}$ level and compose the refinement assertion $\iexp{hm\_assn}$ with the $\iexp{lshm\_rel}$ relation to obtain a full refinement chain for the high level, abstract update and lookup functions.
