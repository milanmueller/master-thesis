For a thorough introduction on PAC, in particular the underlying concepts and their use in verification of digital circuits, we refer to to the work by Kaufmann et al. \cite{pac-2018} \cite{pac-2024} \cite{kaufmann-phd-thesis}.
Here, we only introduce the foundations that are used in PAC checking and are thus relevant to our work on Pastèque:
\begin{itemize}[noitemsep, topsep=0pt, parsep=0pt]
  \item We consider multivariate polynomials $\mathbb{K}[X]$ with variables $X$ and coefficients in field $\mathbb{K}$.
  \item For a set $P \subseteq \mathbb{K}[X]$, a \textit{model} is a point $x$ such that every $p \in P$ is 0 at $x$. i.e. $\forall p \in P. p(x) = 0$.

$I$ is an ideal iff. for all $i_1,i_2\in I$ and $p \in \mathbb{K}[X]$ we have $i_1 + i_2 \in I$ and $p \cdot i_1 \in I$.

\subsection{Isabelle/HOL}\label{sec:isabelle-hol}

The proof assistant \textit{Isabelle} \cite{isabelle} enables the writing of machine-checked formal mathematical proofs.
Following the LCF approach \cite{computational-logic-origins}, Isabelle employs a small kernel of logical inference rules for verifying the correctness of user-defined proofs, such that correctness of the kernel's inference engine implies correctness of the proofs.

To interactively construct proofs, the user can utilize and combine a variety of proof methods, ranging from fundamental deductive concepts, like case analysis and induction, to more complex automated methods.
An example of the latter is the \texttt{smt} method which offloads reasoning work to an external SMT-solver and then reconstructs its returned proof artifact using other proof methods on the Isabelle side to obtain a valid proof that Isabelle's kernel will accept.
Potential errors in a proof method do not lead to acceptance of an unsound proof since the kernel rejects inference steps if they are not valid.

The core Isabelle system, more precisely referred to as \textit{Isabelle/Pure}, is a generic theorem proving framework, meaning it can serve as a basis for implementation of different logical theories with distinct axioms.
The most widespread instance of Isabelle is \textit{Isabelle/HOL}, which is an axiomatization of simply typed higher-order logic on top of Isabelle/Pure.
Isabelle/HOL is also used in this thesis.

% Isabelle has been used for formalizations from various domains, including fundamentals of mathematics, e.g. Gödel's Incompleteness Theorems \cite{Incompleteness-AFP} or the Prime Number Theorem \cite{Prime-Number-Theorem-Avigad} \cite{Prime_Number_Theorem-AFP}, but also the verification of computer systems, for instance in the seL4 OS microkernel \cite{seL4}.

Throughout this thesis, I assume familiarity with simply typed higher-order logic and use notation closely tied to actual Isabelle syntax.
\begin{itemize}
  \item Leading apostrophes indicate type variables, e.g. $\tv{a}$.
  \item $\dbcolon$ is used to annotate the type of a value, e.g. $a \dbcolon \tv{a}$ means that value $a$ is of type $\tv{a}$.
  \item An algebraic datatype $\iexp{ta}$ with type parameters
        $\tv{a_1}, \dots, \tv{a_k}$ and $n$ constructors is denoted by
        $$
          (\tv{a_1}, \dots, \tv{a_k}) \app \iexp{ta}
            = C_1 \app \tau_{1,1} \app \dots \app \tau_{1,m_1}
            \mid \dots \mid
              C_n \app \tau_{n,1} \app \dots \app \tau_{n,m_n}
        $$
        where each constructor $C_i$ carries $m_i \ge 0$ arguments, and each
        argument type $\tau_{i,j}$ is an arbitrary type that may mention the
        type parameters $\tv{a_1}, \dots, \tv{a_k}$ as well as the defined type
        $(\tv{a_1}, \dots, \tv{a_k}) \app \iexp{ta}$ itself, allowing recursive
        datatypes.
  \item Functions are first-class objects and are typically presented in curried form.
        A function $f \dbcolon \tv{a} \rightarrow \tv{b} \rightarrow \tv{c}$ for a given $a \dbcolon \tv{a}$ returns a function of type $\tv{b} \rightarrow \tv{c}$.
  \item For a function $f \dbcolon \tv{a} \rightarrow \tv{b} \rightarrow \tv{c}$, $f\app a\app b$ denotes function application for arguments $a \dbcolon \tv{a}, b \dbcolon \tv{b}$.
  \item $\lambda$ denotes anonymous functions, e.g. $\lambda \app a \app b. f \app a \app b$ is an anonymous function that applies the named function $f$ to arguments $a$,$b$.
  \item For types $\tv{a}$ and $\tv{b}$, $\tv{a} \times \tv{b}$ denotes the product type of tuples $(a \dbcolon \tv{a}, b \dbcolon \tv{b})$.
  \item For a type $\tv{a}$, $\ls{\tv{a}}$ denotes the type of lists with elements of type $\tv{a}$.
        A concrete list is denoted by $[x,y,z]$.
  \item For a type $\tv{a}$, $\set{\tv{a}}$ denotes the type of sets with elements of type $\tv{a}$.
        A concrete set is denoted by $\{x,y,z\}$.
  \item For a type $\tv{a}$, $\tv{a} \app \iexp{multiset}$ denotes the type of multisets with elements of type $\tv{a}$.
        A concrete multiset is denoted by $\{\#x,x,y\#\}$.
  \item I use the following built-in Isabelle types:
  \begin{itemize}
    \item Type $\iexp{bool}$ of booleans,
    \item Type $\iexp{nat}$ of natural numbers (unbounded),
    \item Type $\iexp{int}$ of integers (unbounded),
    \item Type $w \app \iexp{word}$ of machine words with bit-width $w$,
    \item Unit type $\iexp{unit}$ with the only value $\iexp{()}$.
  \end{itemize}
\end{itemize}

\subsection{Isabelle Refinement Framework}\label{sec:isabelle-refinement-framework}
The Isabelle Refinement Framework by Lammich \cite{isabelle-refinement-framework} enables a refinement approach to defining imperative programs and proving correctness properties of such programs. \todo{In motivation, write a section on what the idea of refinement is, and which problem it solves.}
This subsection introduces a simplified view on the underlying \texttt{nres} monad and sketches its usage for defining and verifying imperative programs in Isabelle-HOL.
Most of the algorithms I implemented for this thesis are defined in the \texttt{nres} monad, the exception being fundamental operations on custom datatypes that \refsec{sec:low-level-datatypes-in-isabelle-llvm} introduces.

Nondeterministic computations are represented using the \texttt{nres} monad.
\texttt{nres} over some type $\tv{a}$, representing computations with results of type $\tv{a}$, is defined as
$$
  \tv{a} \app \iexp{nres} = \iexp{FAIL} \mid \iexp{RES} \app (\set{\tv{a}})
$$
Intuitively, for $\iexp{RES \app S}$, the set $\iexp{S}$ represents all possible results of a computation, while $\iexp{FAIL}$ can be seen as a representation of failed computations, such as an out-of-bounds read from an array.

For lifting a value $\iexp{a}$ of type $\tv{a}$ into $\tv{a} \app \iexp{nres}$, the Refinement Framework defines
$$
  \iexp{RETURN} \dbcolon \tv{a} \rightarrow \tv{a} \app \iexp{nres}, \text{ where } \iexp{RETURN} \app \iexp{a} = \iexp{RES} \app \{\iexp{a}\}
$$
As an example, $\iexp{RETURN}$ is used to describe a program $\iexp{sum}$ that computes the sum of two natural numbers as follows:
$$
  \iexp{sum} \dbcolon \iexp{nat} \rightarrow \iexp{nat} \rightarrow \iexp{nat} \app \iexp{nres}, \text{ where } \iexp{sum} \app \iexp{a} \app \iexp{b} = \iexp{RETURN} \app (\iexp{a} \iexp{+} \iexp{b})
$$
The Refinement Framework also defines $\iexp{SPEC}$, parameterized over a characteristic function $\Phi$ to describe results:
$$
  \iexp{SPEC} \dbcolon (\tv{a} \rightarrow \iexp{bool}) \rightarrow \tv{a} \app \iexp{nres}, \text{ where } \iexp{SPEC} \app \Phi = \iexp{RES} \app \{ \iexp{a} \dbcolon \tv{a} \mid \Phi \app \iexp{a} \}
$$
$\iexp{SPEC}$ is typically used to give specifications for programs.
For example, I define $\iexp{add\_spec}$ as a specification for a program that computes the sum of two natural numbers as follows:
$$
  \iexp{add\_spec} \dbcolon \iexp{nat} \rightarrow \iexp{nat} \rightarrow \iexp{nat} \app \iexp{nres}, \text{ where } \iexp{add\_spec} \app \iexp{a} \app \iexp{b} = \iexp{SPEC} \app (\lambda \app \iexp{r}.\, \iexp{r} = \iexp{a} \iexp{+} \iexp{b})
$$
On $\iexp{nres}$, the Refinement Framework defines an order $\le$, given by
$$
\begin{aligned}
  \iexp{\_} &\le \iexp{FAIL} &&\Longleftrightarrow \iexp{True}, \text{ where $\iexp{\_}$ is an arbitrary value} \\
  \iexp{FAIL} &\le \iexp{RES} \app X &&\Longleftrightarrow \iexp{False} \\
  \iexp{RES} \app X &\le \iexp{RES} \app Y &&\Longleftrightarrow X \subseteq Y
\end{aligned}
$$
Intuitively, $\iexp{P} \le \iexp{P'}$ means that every possible result of program $\iexp{P}$ is also a possible result of $\iexp{P'}$.
A program $\iexp{P} \dbcolon \tv{a} \app \iexp{nres}$ is said to \textit{refine} program $\iexp{P'} \dbcolon \tv{a} \app \iexp{nres}$ if $\iexp{P} \le \iexp{P'}$.
In particular, if $\iexp{P'}$ is known to be correct, with respect to some definition of correctness, then $\iexp{P} \le \iexp{P'}$ implies that $\iexp{P}$ is also correct with respect to that definition of correctness.
For instance, $\iexp{P} \app a \app b \le \iexp{add\_spec} \app a \app b$ states that $\iexp{P}$ computes the sum of two natural numbers $a,b$.

Note that $(\tv{a} \app \iexp{nres}, \le)$ is a complete lattice with top element $\iexp{FAIL}$. In particular, a refining program may only fail if the refined program also fails.

The Refinement Framework implements a $\iexp{bind} \dbcolon \tv{a} \app \iexp{nres} \rightarrow (\tv{a} \rightarrow \tv{b} \app \iexp{nres}) \rightarrow \tv{b} \app \iexp{nres}$ operator on $\iexp{nres}$ to enable sequential composition of two programs.
In addition, it provides loops and can be used with Isabelle's builtin $\iexp{if}$ expressions such that typical imperative programs can be expressed.

Statements like $\iexp{P} \app a \app b \le \iexp{add\_spec} \app a \app b$ must be proven in Isabelle by the user.
The Refinement Framework offers tools to automate significant portions of such proofs.
In particular, the $\iexp{refine\_vcg}$ verification condition generator can be used to transform goals expressed in the $\iexp{nres}$ monad to standard Isabelle-HOL goals, on which Isabelle's proof automation (in particular $\iexp{sledgehammer}$) can then often be used effectively.

\subsection{Sepref}\label{sec:sepref}

In general, a program $\iexp{P} \dbcolon \tv{a} \app \iexp{nres}$ cannot be directly translated to an executable program, as it only describes the possible outcomes of a program.
This section gives an informal overview of the Sepref tool \cite{sepref} by Lammich, which is used to synthesize an executable implementation from such a program.

The Imperative-HOL framework \cite{Imperative-HOL} defines a semantics of imperative programs in Isabelle/HOL.
Programs defined in Imperative-HOL can then be exported to Standard-ML code.
Sepref uses a separation logic on Imperative-HOL \cite{Separation_Logic_Imperative_HOL-AFP} which enables reasoning on imperative programs defined in Imperative-HOL.
Note that Imperative-HOL and the separation logic on it are not discussed here, since, for the thesis, I worked with Isabelle-LLVM \cite{isabelle-llvm} (also by Lammich) which can be seen as Sepref's successor and defines its own separation logic on a shallow embedding of LLVM instead of Imperative-HOL (cf. \refsec{sec:isabelle-llvm}).

\subsection{Isabelle-LLVM}\label{sec:isabelle-llvm}

This section gives an overview of the notion of \textit{refinement assertions} in Isabelle-LLVM and the separation logic used to reason about LLVM programs.

Isabelle-LLVM defines a shallow embedding of the LLVM intermediate language (i.e. a formalization of a subset of LLVM) and models the state of memory during the execution of a program.
Details regarding the LLVM embedding and memory model are described in Lammich's paper \cite{isabelle-llvm}.
For the thesis I use a simplified notion of refinement assertions and introduce the following types and functions only informally:
\begin{itemize}
  \item States of memory are reasoned about using a separation algebra $(\iexp{mem}, \#\#, +, 0)$ as defined in the AFP's Separation Algebra by Klein et al.~\cite{Separation_Algebra-AFP}, which is based on the Abstract Separation Logic by Calcagno et al.~\cite{Abstract_Separation_Logic}.
    Isabelle-LLVM instantiates the abstract separation algebra with its memory model.
  \item An \textit{assertion} is a function $f \dbcolon \iexp{mem} \rightarrow \iexp{bool}$ used to make statements about the state of memory.
    I use the type synonym $\iexp{assn} := \iexp{mem} \rightarrow \iexp{bool}$ as type annotation for assertions.
  \item $\iexp{emp}$ is an assertion that evaluates to $\iexp{True}$ iff. the given state is $0$, i.e. $\iexp{emp} = \lambda s. s = 0$.
  \item The separating conjunction operator $\ast \dbcolon \iexp{assn} \rightarrow \iexp{assn} \rightarrow \iexp{assn}$ allows for combination of assertions.
    If $A \dbcolon \iexp{assn}$ and $B \dbcolon \iexp{assn}$ are assertions, then $A \ast B$ is an assertion that evaluates to $\iexp{True}$ for a given state $h \dbcolon \iexp{mem}$, iff. there exists a decomposition $h = x + y$ such that $x \#\# y$ (i.e. $x$ and $y$ are disjoint) and $A \app x$ and $B \app y$.
  \item $\tv{a} \app \iexp{ptr}$ is the type of pointers to values of type $\tv{a}$.
        Note that, for $\tv{a} \app \iexp{ptr}$ to be recognized by the LLVM code generator of Isabelle-LLVM, $\tv{a}$ must be representable in LLVM.
        In particular, the type of machine words, $w \app \iexp{word}$, is the only representable type directly mentioned in this thesis.\\
        For $\mapsto \dbcolon \tv{a} \app \iexp{ptr} \rightarrow \tv{a} \rightarrow \iexp{assn}$, the assertion $(p \mapsto a) \sigma $ evaluates to $\iexp{True}$, iff. $p$ is a pointer to $a$ in state $\sigma$\footnote{$\mapsto$ is based on the assertion $\iexp{ll\_bpto}$, which is defined in the theory $\iexp{Isabelle\_LLVM.LLVM\_DS\_Block\_Alloc}$.}.
        Note that $p \mapsto a$ implicitly states exclusive ownership of the object $p$ points to, as no object can have multiple separate owners in the separation logic.
  \item Similarly to the $\iexp{nres}$ monad, Isabelle-LLVM uses a state error nondeterminism monad $\tv{a} \app \iexp{llM}$ to describe LLVM programs with return type $\tv{a}$. \todo{There should be at least some intuition of what $\iexp{llM}$ does.}
        Note that $\tv{a}$ must be a type representable in LLVM for the code generator to be able to produce code for a program $P \dbcolon \tv{a} \app \iexp{llM}$.
\end{itemize}

To make assertions independent of the state of memory, a boolean value can be lifted to an assertion by $\uparrow \dbcolon \iexp{bool} \rightarrow \iexp{assn}$ where $\uparrow \app b = \lambda h. \iexp{emp} h \land b$.
Note that $A \ast \iexp{emp} = A$ for any assertion $A$.

In Isabelle-LLVM, a \textit{refinement assertion} $A \dbcolon \tv{a} \rightarrow \tv{b} \rightarrow \iexp{assn}$ is a function that produces an assertion for given values of type $\tv{a}$ and $\tv{b}$, where type $\tv{b}$ is representable in LLVM.
Refinement assertions specify how abstract values are represented in LLVM by concrete values.
For example, a refinement assertion $\iexp{si\_assn} \dbcolon \iexp{int} \rightarrow 8 \app \iexp{word} \rightarrow \iexp{assn}$ defines how 8-bit machine words, being interpreted as signed 8-bit integers, refine the abstract HOL type of unbounded integers.
It holds that $\iexp{si\_assn} \app (-128) \app \iexp{0x80} \app 0 = \iexp{True}$, while $\iexp{si\_assn} \app 128 \app w \app \sigma = \iexp{False}$ for any $w$ and $\sigma$, as $128$ is not representable with an 8-bit signed integer.

A \textit{Hoare-triple} $\{\Psi \dbcolon \iexp{assn}\} (P \dbcolon \tv{a} \app \iexp{llM}) \{\Phi \dbcolon \tv{a} \rightarrow \iexp{assn}\}$ states that, if a \textit{precondition} $\Psi$ holds initially, then the program $P$ is executed successfully and the \textit{postcondition} $\Phi$ holds afterwards.
For example, the Hoare-triple
$$
  \{\iexp{si\_assn} \app a \app ai \ast \iexp{si\_assn} \app b \app bi\}
  \app (\iexp{add} \app ai \app bi) \app
  \{\lambda r. \iexp{si\_assn} \app (a + b) \app r\}
$$
can be read as follows:
If 8-bit machine words $ai, bi$ refine the integers $a, b$ then the result of $\iexp{add} \app ai \app bi$ refines the integer $a + b$.
Note that in this particular example, the statement only holds if $a + b$ does not overflow and is therefore representable by an 8-bit machine word.
This requirement can be added to the precondition:
\begin{gather*}
  \{\uparrow(a + b \le 127 \land -128 \le a + b) \ast \iexp{si\_assn} \app a \app ai \ast \iexp{si\_assn} \app b \app bi\} \\
  (\iexp{add} \app ai \app bi) \\
  \{\lambda \app r. \iexp{si\_assn} \app (a + b) \app r\}
\end{gather*}
This addition makes the statement provable by the $\iexp{vcg}$ tool.

As a user of Isabelle-LLVM, one does not typically work with Hoare-triples directly.
Instead, usually the $\iexp{nres}$ monad is used to define algorithms on HOL-types; the $\iexp{sepref}$ tool can then transform high-level programs defined in $\iexp{nres}$ into low-level programs defined in $\iexp{llM}$ and prove respective correctness statements, given by Hoare-triples automatically.

\subsubsection{Ownership in Isabelle-LLVM}\label{sec:ownership-in-isabelle-llvm}
This subsection gives a simplified overview of the ownership model that is implemented in Isabelle-LLVM.

Isabelle-LLVM distinguishes \textit{pure} and \textit{impure} values.
Stack allocated values are pure \todo{fact-check}.
When used as function arguments, they are duplicated and thus retain their value once the callee returns.
Machine words are an example of pure values: Revisiting the example Hoare-triple from \refsec{sec:isabelle-llvm}, the postcondition can be strengthened to
\begin{gather*}
  \{\uparrow(a + b \le 127 \land -128 \le a + b) \ast \iexp{si\_assn} \app a \app ai \ast \iexp{si\_assn} \app b \app bi\} \\
  (\iexp{add} \app ai \app bi) \\
  \{\lambda \app r.\, \iexp{si\_assn} \app (a + b) \app r \ast \iexp{si\_assn} \app a \app ai \ast \iexp{si\_assn} \app b \app bi\}
\end{gather*}
The addition of $\iexp{si\_assn} \app a \app ai \ast \iexp{si\_assn} \app b \app bi$ means that, after being used as arguments for $\iexp{add}$, $ai$ and $bi$ remain valid representations of the original abstract integers $a$ and $b$.

For impure values, this does not hold.
Objects that are heap allocated are always impure \todo{fact-check}.
In particular lists, which are used frequently in Pastèque, are impure in Isabelle-LLVM.
This is an important distinction from the old Imperative-HOL backend in which lists are pure object (as long as the contained elements are also pure) with persistence guaranteed by the compiler.

To illustrate the implications of this observation, assume that for a refinement assertion $A \dbcolon \tv{a} \rightarrow \tv{b} \rightarrow \iexp{assn}$, we have a function
$$
  \iexp{ls\_assn} \dbcolon (\tv{a} \rightarrow \tv{b} \rightarrow \iexp{assn}) \rightarrow \ls{\tv{a}} \rightarrow \tv{b} \app \iexp{llvm\_list} \rightarrow \iexp{assn}
$$
that defines refinement of abstract lists of type $\ls{\tv{a}}$ by an imaginary concrete list implementation $\tv{b} \app \iexp{llvm\_list}$.
Then, the following Hoare-triple could, in principle, be provable with the Imperative-HOL backend:
\begin{gather*}
  \{(\iexp{ls\_assn} \app A) \app xs \app xsi \ast \uparrow(xs \neq [])\} \\
  (\iexp{tl\_impl} \app xsi) \\
  \{\lambda \app r.\, (\iexp{ls\_assn} \app A) \app (\iexp{tl} \app xs) \app r \ast (\iexp{ls\_assn} \app A) \app xs \app xsi\}
\end{gather*}
The Hoare-triple can be read as follows: If the non-empty abstract list $xs$ is refined by a concrete list implementation $xsi$, then, after calling a function that returns a the tail of the list, the abstract tail $\iexp{tl} \app xs$ is refined by the result of the function.
Also, after the function has been executed, $xsi$ still remains a concrete representation of the original list $xs$.
This property typically holds in functional languages where lists are persistent objects, as is the case in the Standard-ML backend.

In Isabelle-LLVM, the above Hoare-triple can never hold.
Lists in LLVM are are a chain of nodes, each carrying a value and a pointer to the next node in the list.
They are therefore heap-allocated, impure objects.
The underlying separation logic requires that there can only be a single reference to a heap allocated object at any point in time.
The Hoare-triple above violates this requirement, as both $r$ and $xsi$ would now reference the same list.
If we weaken the the postcondition, the statement becomes provable in Isabelle-LLVM:
\begin{gather*}
  \{(\iexp{ls\_assn} \app A) \app xs \app xsi \ast \uparrow(xs \neq [])\} \\
  (\iexp{tl\_impl} \app xsi) \\
  \{\lambda \app r.\, (\iexp{ls\_assn} \app A) \app (\iexp{tl} \app xs) \app r\}
\end{gather*}
We lose the assertion $(\iexp{ls\_assn} \app A) \app xs \app xsi$ in the postcondition, we say that the original list $xsi$ was \textit{destroyed}.
\refsec{sec:lists-with-tail-pointers} describes the approach that I chose to address this issue for functions working on lists specifically.
