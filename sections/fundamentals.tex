\subsection{The Practical Algebraic Calculus}

This section introduces the practical algebraic calculus (PAC).
For a thorough introduction on PAC, in particular the underlying concepts and their use in verification of digital circuits, we refer to to the work by Kaufmann et al. \cite{pac-2018} \cite{pac-2024} \cite{kaufmann-phd-thesis}.
Here, we only introduce the foundations that are used in PAC checking and are thus relevant to our work on Pastèque:
\begin{itemize}[noitemsep, topsep=0pt, parsep=0pt]
  \item We consider multivariate polynomials $\mathbb{K}[X]$ with variables $X$ and coefficients in field $\mathbb{K}$.
  \item For a set $P \subseteq \mathbb{K}[X]$, a \textit{model} is a point $x$ such that every $p \in P$ is 0 at $x$. i.e. $\forall p \in P. p(x) = 0$.
  \item A nonemtpy subset $I \subseteq \mathbb{K}[X]$ is called \textit{ideal} if it is closed under multiplication and addition, i.e.
$I$ is an ideal iff. for all $i_1,i_2\in I$ and $p \in \mathbb{K}[X]$ we have $i_1 + i_2 \in I$ and $p \cdot i_1 \in I$.
  \item A set $B = \{ b_1, \dots, b_n \} \subseteq \mathbb{K}[X]$ is a basis of an ideal $I$, if $I = \{q_1 \cdot b_1 + \dots + q_n \cdot b_n \mid q_1, \dots, q_n \in \mathbb{K}[X]\}$, we denote this by $I = \langle B \rangle$.
\end{itemize}

\subsection{Isabelle/HOL}\label{sec:isabelle-hol}

The proof assistant \textit{Isabelle} \cite{isabelle} enables the writing of machine checked formal proofs for properties of mathematical objects.
Following the LCF approach \cite{computational-logic-origins}, Isabelle employs a small kernel of logical inference rules for verifying the correctness of user-defined proofs, such that, in principle, correctness of the kernels inference engine implies correctness of the proofs. \\
To interactively construct proofs, the user can utilize and combine a variety of proof tactics, ranging from fundamental deductive concepts, like case analysis and induction to more complex automated methods.
An example of the later is the \texttt{smt} tactic \todo{Reference} which offloads reasoning work to an external SMT-solver and then reconstructs its returned proof artifact using other proof tactics on the Isabelle side to obtain a valid proof that Isabelle's kernel will accept.
Potential errors in a proof tactic will not lead to acceptance of an unsound proof since the kernel will check and potentially reject inference steps if they are not valid.
By relying on only a small kernel to be correct, proofs accepted by Isabelle have a high probability of being correct, compared to other approach to computational logic which might rely on large code bases, with many inference rules and special cases, to not contain errors. \todo{Give some examples of that}

The core Isabelle system, more precisely referred to as \textit{Isabelle/Pure}, is a generic theorem proving framework, meaning it can serve as a basis for implementation of different logical theories with distinct axioms.
The most widespread instance of Isabelle is \textit{Isabelle/HOL}, which is an axiomatization of simply typed higher order logic on top of Isabelle/Pure, which is also used in this thesis.
We will refer to Isabelle and Isabelle/HOL interchangeably in the following sections.

Isabelle has been used for formalizations from various domains, including fundamentals of mathematics, e.g. Gödel's Incompleteness Theorems \cite{Incompleteness-AFP} or the Prime Number Theorem \cite{Prime-Number-Theorem-Avigad} \cite{Prime_Number_Theorem-AFP}, but also the verification of computer systems, for instance in the seL4 OS microkernel \cite{seL4}. \\
In this thesis, we use Isabelle for the formal verification of computer programs, meaning we consider an abstract, formal model of a program and then use Isabelle's proof tactics to verify correctness properties of that model, which we then relate to correctness of the concrete program.\\
An intrinsic challenge with this approach is the accuracy of our model, since correctness of the model is meaningless if the model does not accurately represent the behavior of the program's implementation.
This is particularly challenging if the concrete program is an implementation in a high level language, for which it might be challenging to formally specify the language's semantics \todo{example}.

I used the framework Isabelle-LLVM \cite{isabelle-llvm} which employs top-down refinement to start with an abstract model and then iteratively move towards the concrete implementation, ultimately generating verified LLVM-IR code, contrary to to the previously described approach of abstracting an existing concrete program.

In general, a program \inlinecode{P :: 'a nres} can not be directly translated to an executable program, as it only describes the possible outcomes of a program.

The Sepref then exports Standard-ML code, which is therefore the case for the original implementation of Pastèque by Fleury \cite{pac-2024}.

\subsection{Isabelle-LLVM}\label{sec:isabelle-llvm}

The newer Isabelle-LLVM framework \cite{isabelle-llvm}, also by Lammich, uses the same \inlinecode{nres} monad, but instead of Standard-ML, it generates LLVM code.
The verified SAT-solver IsaSAT by Fleury \cite{isasat-sml} saw an increase in performance by factor two \todo{check number}, when migrated from the Standard-ML backend to LLVM \cite{isasat-llvm}.
This observation motivated the migration of also Pastèque from Standard-ML to LLVM, which is the primary objective of this thesis.

This section gives a simplified overview on the notion of \textit{refinement assertions} in Isabelle-LLVM.
Details regarding the LLVM memory model are described in Lammich's publications \cite{isabelle-llvm} and are omitted here.

A refinement assertion \inlinecode{A :: 'a => 'b => bool} defines how abstract values of type \inlinecode{'a} are related to concrete values of type \inlinecode{'b} that are representable in llvm.
For example, a refinement assertion \inlinecode{si_assn :: int => 8 word => bool} defines how 8-bit machine words, being interpreted as signed 8-bit integers, refine the abstract HOL type of unbounded integers.
It holds that \inlinecode{si_assn -128 0x80 = True}, while \inlinecode{si_assn 128 w = False} for any \inlinecode{w}, as 128 is not representable with an 8-bit signed integer.

The conjunction operator \inlinecode{**} allows for combining refinement assertions, e.g. \inlinecode{A a ai ** B b bi} states that \inlinecode{ai} refines \inlinecode{a}, as defined by refinement assertion \inlinecode{A}, while \inlinecode{bi} refines \inlinecode{b}, as defined by refinement assertion \inlinecode{B}.

\textit{Hoare-triples} are used to make statements about the effects of programs.
\inlinecode{\<Phi> P \<Psi>} states that, if the \textit{precondition} \inlinecode{\<Phi>} holds before the execution of program \inlinecode{P}, then the \textit{postcondition} \inlinecode{\<Psi>} holds afterwards.
