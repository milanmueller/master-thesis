\section{Discussion}\label{sec:discussion}

This section contains a discussion of the results of the evaluation in \refsec{sec:evaluation}.
It also introduces some possible further directions of the Pastèque development.

Subsections \refsec{sec:ai-usage-discussion} and \refsec{sec:takeaways} close the thesis by a subjective discussion on the use of generative AI tools and my general experience of working with Isabelle and Isabelle-LLVM.

\subsection{Evaluation Results}\label{sec:evaluation-results}
The main evaluation in \refsec{sec:comparison-of-all-checkers} has shown that, for smaller instances, Pastèque with the LLVM backend is faster and uses less memory compared to the Standard ML backend.
For the large 512-bit multipliers however, the LLVM backend is slower.

Breaking down the runtime into separate phases in \refsec{sec:pasteque-breakdown} indicates some progression for the LLVM backend in Figure~\ref{fig:phase-comparison} towards larger instances as the relative amount of time spent on parsing and checking increases for larger instances.
Yet, this observation does not imply a clear reason for the subpar scaling behavior of the LLVM backend, as both parsing and checking use multiple data structures and operations making it impossible to pin down a singular operation or data structure as the culprit.

The fuzzing based parser evaluation in \ref{sec:simple-pac-fuzzer} shows that, with increasing number of digits in coefficients, the LLVM backend takes more time to parse input files.
the number of digits in coefficients affects the string to multiple precision integer conversion, discussed in \ref{sec:conversion-between-string-and-integer}, implying that this conversion is done more efficiently in the Standard ML backend.
A potential improvement to the conversion would be to partition a given string into blocks of multiple digits, which can be represented by a single limb, then multiply the accumulator by $10^l$, where $l$ is the number of digits in a block, and then add the block to the accumulator.
It not clear however, how large the effect of this optimization on the overall runtime with 512 bit instances would be.

\subsection{Further Improvements to Pastèque}\label{sec:future-development}
This section discusses some potential improvements to the Isabelle-LLVM migration which might further improve its performance and/or code quality.

Using the currently developed fractional separation logic for Isabelle-LLVM \cite{isabelle-llvm-fractional} in Pastèque might obsolete my custom workarounds of (interleaving) fold-based read only operations on lists (cf. \refsec{sec:non-destructive-list-access-using-fold}, \refsec{sec:interleaving-fold}) and the fused addition (cf. \refsec{sec:avoiding-polynomial-deep-copies}) while also making it possible to further avoid deep-copy operations.

Another optimization that could already be carried out without fractional separation logic might be to represent to terms in monomials by arrays instead of lists, as is currently the case.
This optimization might speed up comparison between terms, allowing to shortcut comparison when array lengths are unequal and would certainly reduce the total number of allocations.

Furthermore, the current design of partial maps (cf. \ref{sec:partial-maps}) wraps the buckets, represented by linked lists, by an extra pointer dereference through $\iexp{box\_assn}$.
It might be possible to eliminate this extra layer from the refinement assertion to further reduce the total number of allocations and pointer dereferences.

Another possible change to Pastèque would be to move parsing to the Isabelle side such that the C side only handles IO and hands the files directly as strings to the verified LLVM code.
While it is unlikely that this change would improve performance, it would reduce the amount of trusted parsing code and allow for a verified parsing process.
However, one would have to formally define a semantic for the given input files to obtain a meaningful correctness proof which is a non-trivial task.

\subsection{AI-Assisted Proof Development}\label{sec:ai-usage-discussion}
When starting to work on this thesis, I initially set a goal of not using any generative AI tools for Isabelle proofs or implementation.
For the initial work of extending the multiple precision integer arithmetic library, discussed in \refsec{sec:multiple-precision-integers}, I had followed that goal and did non use generative AI tools \footnote{For the final implementation of conversion between integer and string, I did use AI to write parts of the proofs.}.
Once I moved onto the Isabelle-LLVM migration and realized that I would have to implement fundamental low-level data structures, discussed in \refsec{sec:low-level-datatypes-in-isabelle-llvm}, I gave up on the goal of not using AI tools after failing to proof correct even simple fundamental operations by myself.
I then started to use the tool Claude Code by Anthropic, using different versions of the language models "Opus", "Sonnet" and "Fable", by copying proof goals into Claude Code and task it to analyze the goal and draft initial proofs, which I would then copy back into the actual Isabelle theories.
Often, the generated proofs were not accepted by the Isabelle kernel directly and I could use Isabelle's built in proof automation, in particular sledgehammer, to discharge failing steps in the proof.
Some parts of the final theories, in particular the theory $\iexp{LLVM\_DS\_Char\_Literals}$ which contains refinement of printable ASCII characters, were directly generated by Claude Code.

Compared to using a web-based chat interface, using a local installation of an "agentic" tool like Claude Code has the advantage that the tool will use command line tools like \inlinecode{grep} to add relevant definitions from the Isabelle-LLVM library to its context window which, in my experience, improves the quality of its outputs significantly and makes it a viable tool for this use case.

In my opinion, using a tool like Claud Code with theorem provers like Isabelle where results are checked by a deterministic kernel based on a rigorous formalization of fundamental logic, might often be a better option than generating large amounts code in unverified general purpose languages where adherence to a specification is not expressed formally and thus hard to determine.
I would not be surprised to see formal methods being integrated increasingly often into future approaches to software development based on generative AI tools.

\subsection{Personal Conclusion}\label{sec:takeaways}
Using theorem provers like Isabelle allows for rigorous correctness proofs even for complex problems far beyond the scope of fully-automated tools.
For the use-case of software verification, theorem provers are typically limited to pure functional implementations which, compared to languages like C or Rust, necessitates a garbage collector and comes at a performance penalty.
While some particular low-level optimizations like bit-stuffing or pointer arithmetic are not possible in Isabelle-LLVM, it still moves moves the formally verified approach significantly closer to high-performance languages by enabling simultaneous development and verification of imperative programs with manual memory management while also allowing for elegant correctness proofs through its step-wise refinement approach.
Im convinced that my work on the Pastèque migration to Isabelle-LLVM is not representative of Isabelle-LLVM's full potential regarding efficiency and that it would be possible to improve the LLVM migration to supersede the performance of the Standard ML implementation of Pastèque in 512-bit instances aswell.

My personal biggest struggles of working with Isabelle-LLVM mostly stem from lack of introductory documentation, ie. a "beginner tutorial" specific to Isabelle-LLVM, extending the quickstart guide of the imperative refinement framework \cite{Refine_Imperative_HOL-AFP} with information on how to work with $\iexp{llM}$-level functions directly.
Another hurdle is intrinsic to its approach of being implemented as proof methods for Isabelle; when refining functions with \inlinecode{sepref} or proving $\iexp{llM}$-level theorems with \inlinecode{vcg}, there are no error messages when something does not go as expected.
Instead, the tools provide feedback through unresolved goal states which are often lengthy and contain symbols and definitions from the underlying separation logic, which are usually hidden from the user when writing theorems.
To productively work with Isabelle-LLVM, it takes significant amounts of time to obtain enough intuition to interpret the returned goal states.
In particular the \inlinecode{vcg} tool might run into unprovable goal states as a result of over eager simplifications by the user which I often could not detect.
I had to resort to using Claude Code to overcome such situations, which I originally wanted to avoid.

With that being said, I found Isabelle-LLVMs interactive approach to formal verification of complex software to be immensely insightful, being a hands-on combination of theory and practice that I have not seen anywhere else during my studies of computer science.
