\section{Finalization of the LLVM-migration}\label{sec:finalization-of-llvm-migration}
In addition to the conversion between strings and multiple precision integers, discussed in \refsec{sec:multiple-precision-integers}, and the fundamental datatypes, discussed in \refsec{sec:low-level-datatypes-in-isabelle-llvm}, some more setup is required to finalize the migration of Pastèque to Isabelle-LLVM.
This remaining work and some performance-oriented optimizations are discussed in this section.

\subsection{A new Parser for Pastèque}\label{sec:pasteque-parser-c}
The original Pastèque implementation employs an unverified parser written in Standard ML which constructs the inputs for the verified checker from the given input files.
Concretely the parser must construct (refinement targets of) the following input for the verified checker:
\begin{enumerate}
	\item A specification of type $\iexp{llist\_polynomial}$.
	\item A list of input polynomials of type $\iexp{llist\_polynomial} \app \iexp{list}$, the polynomials $\iexp{sllist\_polynomial}$ with shared variables are constructed on the verified LLVM side.
	\item A list of proof steps of type $\iexp{pac\_step} \app \iexp{list}$.
\end{enumerate}
For the Isabelle-LLVM migration, I write a custom parser in C that constructs these inputs.
To enable writing of such a parser, I export fundamental functions to construct (lists of) polynomials and proof steps directly from C.
The C parser first runs a lexer to obtain an array of tokens, based on the original PAC syntax as defined in \cite{pac-2024}, and then calls the exported list construction functions to directly built the inputs expected by the verified checker code.

The Isabelle-LLVM code generator not only generates \inlinecode{.ll} files containing LLVM code but also C-header files to allow for conveniently calling the verified LLVM functions from c-code.
The header generation has a notable limitation however; the code generator is unable to represent the type of 1-bit integers (i.e. booleans), which are used in the signed multiple precision integers to store their sign, in the generated c-header files.
As the type signature of input polynomials contains signed multiple precision integers, significant parts of the functions required by the C parser can not be included in the generated header files as that would require representing the 1-bit integers.
The header file for the respective functions relying on this datatype is therefore created manually.
Importantly, this has no effect on the LLVM code generation and thus does not affect correctness guarantees of the exported LLVM code.

\subsection{Avoiding Deep-Copy Operations on Polynomial Retrieval}\label{sec:avoiding-polynomial-deep-copies}
As discussed in \refsec{sec:partial-maps}, I use a custom partial map implementation to store a lookup table of polynomials which is referenced in arithmetic operations defined by the input proof steps.
I originally designed the lookup function of the partial maps so that polynomials were cloned on retrieval and the partial map is kept intact afterwards.
Early tests have shown however that this decision had a more significant impact on the Pastèques performance than I had anticipated.
To improve performance, I have implemented a workaround to allow for moving a retrieved polynomial out of the map, instead of cloning it.

		}]{fused-add.pseudo}
The pseudo-code in \refalgo{algo:polynomial-move} illustrates this approach for a partial map $A$, a position $i$ and an accumulator $r$.
To compute $r' := r + p$, I create a fused addition operation that first moves the respective polynomial $p$ at position $i$ out of the partial map $A$, performs the addition (which is proven to not modify $p$) and then finally update $A$ at position $i$ to again carry $p$.
It is then possible to prove that $A$ has the same state after the fused operation as before.

\subsection{Left-Consuming Interleaving Fold}\label{sec:left-consuming-interleaving-fold}
The interleaving fold, introduced in \refsec{sec:interleaving-fold} in the presented form allows for a simultaneous read only walk on two linked lists.
In the actual Pastèque implementation, the linear combination steps do not combine two existing polynomials from the table of input polynomials, but rather update an accumulator polynomial by each given summand (which is computed using polynomials from the table).
Using the original interleaving fold constructs a new polynomial for each summand (as sketched out in the pseudo code \refalgo{algo:polynomial-move}) which means that the previous accumulator must be freed manually.
To avoid this manual (deep) free operation, I implement a variant of the interleaving fold that only keeps its right input list intact and frees the respective node of the left input list in each iteration.

\subsection{A new Error Path}\label{sec:a-new-error-path}
The partial map implementation from \refsec{sec:partial-maps} effectively introduces an upper bound of $2^{63}-2$ on the indices of polynomials in the update operation as discussed in \refsec{sec:low-level-refinement-of-lists-of-optionals}.
An upper bound of $2^{63}-1$ directly follows from $\iexp{sn64\_assn}$ meaning it is effectively encoded on the refinement assertion level.
The $2^{63}-2$ upper bound on the map update however is not encoded by the $\iexp{pmap\_assn}$ partial map refinement assertion, so I add a runtime check and a new error message for the polynomial index of exactly $2^{63}-1$.

It should be noted that none of the benchmark instances, discussed in \refsec{sec:evaluation}, has triggered this case.
The largest observed index in the "sparrc-512" instance is 6013954 so well below $2^{23}$.
An experimental modification of an input file to use $2^{63}-1$ as an index has triggered the new error path in the LLVM backend and has led to a runtime exception in the Standard ML backend which does not have the explicit runtime check.
